What the Sentry bridge shows vs the ouo SDK

sentry-demo agent, 2026-10-17. One journey with real simulator taps in examples/sentry-mobile parallel mode (OUO_SDK=1): @sentry/react-native 8.30.0 goes through the ouosentry bridge, and @ouo/react-native 0.2.0 runs in the same app. The two data sets are compared field by field in Loki, Tempo, Mimir, rum-api and the Grafana plugin. Every gap is classified and the (a) gaps have an effort estimate. Nothing was fixed.

Summary

11(a) gaps: the bridge can fix them from data Sentry already sends; about 11 engineer-days for ten of them, source maps (A10) are roadmap work
4(b) gaps: Sentry never sends the data, so only the ouo SDK can provide it
9(c) cosmetic or plugin issues (most affect both producers)
93 vs 9timeline events for the same 81 s of use: bridge session vs ouo-SDK session (run 2)

3 vs 2errors in the bridged session vs Sentry's own session counter, an (a) bug

The founder's remark "not all information shows" mostly comes from the bridge, not from Sentry. On this journey the bridge already gives a richer timeline than the ouo SDK:

  • taps with component names
  • every request
  • console output and Sentry logs
  • app lifecycle
  • native crashes
  • custom spans and app-start spans

The data it loses is data Sentry does send. It falls into seven groups, all listed as (a) items below:

  • mobile vitals (app start, time to initial display, slow and frozen frames)
  • error context (locale, network, memory, current screen, tags)
  • native crash addresses
  • back navigation
  • release, environment and device fields on some records
  • the timeline for sessions without a replay
  • one counting bug

What only the ouo SDK can add (b):

  • a span for every request, including requests outside a Sentry transaction
  • the session id on backend spans and logs
  • backend correlation without changing Sentry's config
  • replay and masking that ouo controls

In the other direction, the ouo SDK has real gaps today. It does not capture native crashes, errors sent through Sentry.captureException, app start or vitals, custom spans, logs, or tap targets. So the upsell is not "more data" yet: see below.

Setup

  • Stack: isolated compose project ouo-cmp on released images collector, grafana and rum-api 0.2.0 (GHCR). Ports: Grafana 3009, rum-api 8097, Loki 3109, Tempo 3209, Mimir 9019, OTLP 4378, replay 4379, bridge 4380, backend 8089. The ouo, ouo-8a, ouo-sb and ouo-taps stacks were not touched. The demo backend reused the image built for ouo-sb, because a Docker Hub pull of golang:1.26 timed out; examples/backend has not changed since 2026-10-06.
  • App: Release build for a dedicated simulator, "ouo-cmp iPhone 18 Pro" (iOS 27), with these settings:
    • Sentry DSN on localhost:4410, where sentrytap records every request and forwards it to the bridge (upstream: none).
    • ouo SDK exporting to the same collector as service sentry-demo-ouo.
    • Bridge service name sentry-demo.
    • Sentry: tracesSampleRate 1, replaysSessionSampleRate 1, masking off, enableLogs, propagateTraceparent: true.
  • Journey (real UIKit taps through the simulator tool):
    1. Browse catalog, fetch products, fetch 500, XHR cart, checkout, failed checkout.
    2. Product screen, add to cart, cart, back to Home.
    3. Scroll; handled error, unhandled rejection, breadcrumb + message, flush.
    4. Home button for 40 s, then relaunch (new session on both sides).
    5. Search, fetch, JS fatal; relaunch; fetch, native crash; relaunch; background 40 s; relaunch.
  • Demo app changes made for a fair test (no product change):
    • Parallel mode never wired ouo's navigationStateListener or RUMProvider, so run 1's ouo sessions have no screens at all. App.tsx now wires both, as the SDK README says.
    • New build flag OUO_REPLAY=0 turns off the ouo replay.

Where the bridge is ahead of the ouo SDK today

The upsell pitch ("move to the ouo SDK for more") is not true yet on this journey. These are ouo SDK gaps, not bridge gaps, listed so nobody promises them:

  • Native crashes: the ouo SDK records the session as "terminated, healthy" (no exception, no crash count). The bridge has EXC_BAD_ACCESS with mechanism and frames.
  • Errors reported through Sentry.captureException never reach the ouo SDK. An app moving to ouo must call captureError instead (a code change).
  • App start, TTID, slow and frozen frames: Sentry measures them. The ouo SDK has nothing (and the bridge does not show them yet, A4).
  • Custom spans (checkout, submit order, app-start phases): the ouo SDK has no span API.
  • Logs and console: the ouo SDK has no log API.
  • Tap targets ("action-checkout", the component path), app lifecycle, successful requests on the timeline.
  • Device model without extra app code, trace id on errors, in-app frames and stable paths (the ouo stack has per-install container paths, so the same error looks different on every device).

What the ouo SDK really adds today:

  • every request traced (B1)
  • session-scoped backend logs and traces (B2)
  • ouo session rules (B3)
  • replay that ouo controls, independent of Sentry quotas (B4)
  • no Sentry dependency

Parallel-mode findings (only when both SDKs run)

  • Trace ownership: ouo, initialised last, sets traceparent, so backend spans join ouo traces and the bridged traces have 0 backend spans (Tempo run 2: 15 bridge traces, none with backend spans). The pitch demo must use Sentry alone, or the bridge looks worse than it is (F3 verified 27/27 joined without ouo).
  • Two identities: Sentry install id ECD79EDB… vs ouo anonymous id d2b05f50…, and two session ids with the same start time. Pair them by time or by a shared setUser.
  • Sentry breadcrumbs include ouo's uploads (POST :4378/v1/traces, /v1/logs) as timeline requests. shouldCreateSpanForRequest filters spans, not breadcrumbs; a beforeBreadcrumb filter in the demo would hide them.
  • Run 1 Sentry replay cut short: 41 s of a 128 s session, 6 segments then nothing, 0 touches, only 2 taps. Run 2 (ouo replay off) and run 3 (ouo replay on, same journey) were complete: 82 s / 32 touches and 90 s / 28 touches. Not reproduced, so not attributed to the ouo replay. Run 1 was the first launch after a fresh install on a new simulator. Kept open: rerun a few times before claiming the replays are compatible.
  • The demo did not wire ouo navigation or RUMProvider, so earlier parallel runs had no ouo screens and no touch activity. Fixed in examples/sentry-mobile/App.tsx.

What to tell the two clients

  • Day one, DSN change only:
    • crash-free and errored sessions matching Sentry (after A1)
    • a replay with taps for sampled sessions
    • a timeline of screens, errors, failed requests and Sentry logs
    • app spans in Tempo
    Sentry keeps receiving everything byte-identical.
  • Backend correlation needs one line: propagateTraceparent: true in Sentry.init, plus tracePropagationTargets for their API. That is an app release, but no SDK change. Without it, Tempo has app spans only.
  • After the (a) work (about 2.5 weeks of one engineer):
    • vitals (app start, TTID, frozen frames)
    • full error context and usable native stacks
    • back navigation
    • a timeline for unreplayed sessions
  • Do not claim yet that the ouo SDK shows more. It shows less on crashes, vitals, spans and logs until the SDK closes those gaps. Sell it on every request traced, session-scoped backend data, ouo-owned replay and dropping the Sentry bill.
