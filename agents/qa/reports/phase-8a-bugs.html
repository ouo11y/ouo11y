Details

minor 1. Resource attributes leak into custom-event attributes in the timeline

Where
GET /v1/sessions/{id} timeline entries of type custom; rendered under the event name in the plugin Session detail.
Seen
Web session d6eedf18: add_to_cart shows ouo_project_id=demo product_id=p-1001 qty=1; checkout_submitted shows item_count=1 ouo_project_id=demo payment_method=card total=129. Mobile session 6a3c20eb: cart.added shows device_manufacturer=Apple device_model_identifier=arm64 device_model_name=Simulator iOS ouo_project_id=demo product_id=p-1001 product_price=129 session_previous_id=….
Why it matters
ouo.project.id is new in 8a (stamped by rum-api on the resource and promoted to a Loki label/structured metadata by the collector); the timeline builder treats every unknown Loki field as a custom attribute, so every custom event now carries the project id and, on mobile, the whole device resource. Noise, not data loss.
Reproduce
curl -s -H 'Authorization: Bearer rt_dev_0000000000000000' \
  'localhost:8090/v1/sessions/d6eedf18-04e7-40b5-be33-ec535335df53' \
  | python3 -c 'import json,sys; [print(e["name"], e.get("attributes")) for e in json.load(sys.stdin)["timeline"] if e["type"]=="custom"]'
Suggested fix
Filter the resource-derived labels (ouo_project_id, device_*, session_previous_id, …) from the custom-attribute set in the timeline builder, the same way service_name and friends already are.

minor 2. RN SDK: one fatal error, two exception records

Where
@ouo/react-native 0.2.0, Expo 57 dev build on the iOS simulator (examples/mobile).
Seen
Metro log after Chaos > "Fatal error (crash)": [ouo] event exception {… "ouo.exception.fatal": true}, then [ouo] fatal error, writing crash marker and flushing, then a second [ouo] event exception {"exception.message": "Error: Fatal error from the Chaos screen (setTimeout)", … "ouo.exception.fatal": false}. rum-api session 6a3c20eb: timeline exception (fatal) 16:03:58.973, session.end crash .976, exception .984; counts error_count: 1, crash_count: 1 although no handled error was triggered.
Hypothesis
The dev-mode LogBox re-reports the uncaught error through console.error ("Error: Error: …" double prefix), and the SDK's console hook records it as a handled exception. Likely dev-only; check a release build.
Reproduce
Run the dev client against the 8a stack, Chaos > "Fatal error (crash)", relaunch the app, then GET /v1/sessions/<id> with the read token and look at the last three timeline entries and error_count.

observation 3. Dev-only 1-span HTTP POST traces at crash time

Seen
Mobile session 6a3c20eb lists two traces HTTP POST, 1 span, at 19:03:58 and 19:03:59 (exactly the fatal error time), no backend join. Everything else in the session joins demo-backend.
Hypothesis
LogBox POSTs to Metro's /symbolicate; the SDK's fetch instrumentation traces them. Suggest adding the Metro origin to the built-in ignore list when __DEV__.

environment 4. Keepalive upload on unload: delivered on navigation, dropped on pane tab close

Setup
Web demo on http://localhost:5174 (Vite), rum-api localhost:8090, Claude desktop browser pane (Chromium).
Seen
Session d6eedf18: before closing the tab last_seq=7. Two clicks then tabs_close: no new chunk; the next page load continued at seq=10, so the SDK had cut seq=9 on pagehide but its keepalive POST never reached rum-api (ingest counter signal=replay shows no rejection either). Two clicks then a cross-origin navigation in the same tab: seq=11 (14 events, plain JSON) arrived and was accepted, counted outcome=ok. Final meta: seqs [0..8, 10, 11]; rum-api tolerates the gap.
Reading
The keepalive path with the token works on navigation (the browser-only behaviour the SDK summary asked to confirm). The lost chunk on tab close is most likely the pane destroying the renderer before the keepalive request is issued; stock Chrome keeps keepalive requests alive after tab close. Re-check once in a normal Chrome window before calling it an SDK bug.

environment 5. iOS: expo.extra is baked by xcodebuild, and a bare RN debug app picks Metro on 8081

Seen
First build via xcodebuild without the env: the app initialised with rumApi: http://localhost:8080 (the main stack's old rum-api, 404 on /ingest/otlp) although Metro was started with EXPO_PUBLIC_RUM_API=http://localhost:8090. mobilestore.app/EXConstants.bundle/app.config carried the defaults: expo-constants evaluates app.config.ts during the Xcode build (get-app-config-ios.sh), not at Metro time. Rebuilding with the variables exported (or in examples/mobile/.env) fixed it. The app also auto-connected to another session's Metro on 8081; xcrun simctl spawn booted defaults write dev.ouo.mobilestore RCT_jsLocation "localhost:8091" redirects it (deep links need the real scheme dev.ouo.mobilestore://, and without expo-dev-client they do not switch servers).
Suggestion
Say in examples/mobile/README.md and the fast-tracked guide that the env must be present for npx expo run:ios / xcodebuild, not only for expo start. Recorded in kb/e2e-scenario.md.

observation 6. Plugin "Reset then save empty": the key is dropped, no stale "configured"

Seen
Config page: Reset, Save with the field empty, page reloads: no "configured" badge, no Reset button; GET /api/plugins/ouo-rum-app/settings returns "secureJsonFields": {}; the proxied /rum/v1/stats/health is 401 (rum-api sees no usable Bearer); the 401 banner appears on the app pages. Restoring via POST /api/plugins/ouo-rum-app/settings with secureJsonData.readToken (or restarting Grafana so provisioning re-applies) brings secureJsonFields.readToken: true and 200 back. The quirk feared in kb/grafana-app-plugin.md ("saving an empty string still shows configured") does not occur on Grafana 13.2.1; the kb line can be rewritten.
