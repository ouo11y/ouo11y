## Review round 1 (2026-11-04, reviewer session at d152b37)

Fixed:
- **B1, a hang the user leaves the app during was dropped**: `HangDetector.interrupt(now, lastAnswer)` replaces `reset()` and ends a hang in progress at the main thread's answer, or else when the main thread ran `onStop`. It is reported like any hang, and `run.json` no longer keeps a stale hang (which would have made a later SIGKILL `watchdog`). A debugger still drops the hang, and clears it from `run.json`. Unit test `aHangTheUserLeavesTheAppDuringIsReported`.
- **B2, foreground service importance**: `Termination.decide` accepts only importance 100 and 200. The test adds 125 (a backgrounded app's foreground service) and 230 (perceptible) as non-terminations, and 200 as a termination.
- **B3, foreground count**: the count seeded from importance at `init` could reach 2 when the module started before `MainActivity.onStart`. It is now a set of started activities, with `foreground` seeded at `init` and then set from the set on every `onStart` / `onStop`, on the main thread.
- **B4, run state race**: `updateRun { }` changes the state and queues its write under one lock, so the JS thread, the watchdog and the main thread lose no change, and the single io thread writes the states in order.
- **S1**: the spec's C3 termination paragraph no longer gives `launch_timeout` for Android; it points to the Android bullet.
- **S2**: in the background the watchdog parks on a monitor that `onStart` notifies, instead of waking every 200 ms. Spec and `sdk/android/README.md` say so.
- Minor fixes: `startedForActivity` checks that the start record is this pid's; ADR-0016 points to ADR-0017.
- **C10.1 race** (the reviewer's suite run failed it): `rum.feedback()` requested the screenshot frame before stamping the record. In session mode, with the last capture seconds old, the frame was taken at once, often in the record's own millisecond. A still Cart never draws again, so no frame came after it. The record is now emitted first and the frame requested after it (shared JS, iOS RN too). A unit test checks the order and fails on the old code. On a very fast device the frame could still share the ms (post to main + view walk < 1 ms); N82's dedicated feedback frame removes that for good.

Left as follow-ups (agreed with the reviewer as minor):
- FrameMetrics counts only Activity windows, so a React Native `Modal` (a Dialog window) is not counted, while part 1's Choreographer counter was. Fix: listen on every window the app adds (`WindowManager` / `Window.Callback`) or count Choreographer frames while a Dialog is shown.
- A JVM crash report carries the top-level throwable's frames only; the causes are only in the message. Sentry sends each cause as a chained exception, so a later change can add the causes' frames to the report.

Verified after the fixes: `:signals-core:test` 8/8, `:replay-core:test` 18/18, `:signals:assembleRelease`; the RN module's vendored copy re-synced (`npm run -w sdk/react-native build`); RN SDK 200 tests and typecheck; `lychee --offline` 0 errors; `tests/e2e/mobile-android/run.sh` on a fresh AVD and env: 19/19, L2 on C1–C11. The build before the fix was not run on the device: the drop is plain from the code (`reset()` ran before any tick saw the answer). Emulator, AVD and env removed afterwards.

## Review round 2 (2026-11-04)

- **C3.1 false hang at a slow cold start** (my suite run 2): the watchdog's `lastAnswer` baseline was set when `Signals` initialized (module OnCreate), not when the watchdog started. When JS installed the reporter 2 s or more later, the first tick read init → first answer as a hang (2.6 s, stamped before `session.start`). Older than this round. Fixed: `run()` sets the baseline at its start (commented); leaving the park already resets it.
- **B5, no frames on about 1 cold launch in 4** (the reviewer's 6-launch loop; mine had 3 of 12): `MainActivity.onResume` ran before `Signals` registered its lifecycle callbacks, and `appContext.currentActivity` was still null at OnCreate, so no window was ever measured. Confirmed with an instrumented build: the 3 launches with `attachCurrent null` and no `resumed` callback were exactly the 3 sessions with `frames: null`, and the other 9 had 69–112 frames. Fixed in the module: `OnActivityEntersForeground`, `installCrashReporter`, `getAppStartInfo` and `getFrameStats` attach again once the activity is known (idempotent per window).
- **C8.3 can fail on Android** when the screen is still for more than 1.5 s before a crash: the replay ends at the last draw, not at the crash (part 1's session-mode pacing). My run 2 had 1.88 s. Tracked as checklist N92 (close the chunk at the crash time), not hidden in `run.sh`.

Verified for round 2: the B5 loop (force-stop, cold start, Product → Cart → Products, flush), 12 launches before the fix (3 with no frames) and 24 after (all with frames, 66–119). A build with the OnCreate attach removed tests the retry path: 4 of 4 launches attached later and had frames. The final head (debug logs removed): `:signals-core:test` 8/8, `:replay-core:test` 18/18, `:signals` and `:replay` assembleRelease, RN 200 tests and typecheck, lychee 0 errors, the suite 19/19 (L2 C1–C11).
