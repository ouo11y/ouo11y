N6 on the iPhone 16 Pro Max

iPhone 16 Pro Max, iOS 18.6.2, 2026-10-23 (N22, examples/sentry-mobile/scripts/perf/n22_device.py). #40 does not help on the device. ouo holds the main thread 40 ms per capture before and 44–45 ms after, against Sentry's 21–23 ms in the same traces. The main-thread snapshot (view walk + drawHierarchy) is 47–49 ms; the work #40 moved to a queue (compose) is 5.7 ms. After #40 the app also captures more often (95 vs 73–83 per run). By the decision rule, the device still misses Sentry: checklist N51. All three crash flows pass on the phone; a crash in the first second loses the session start (N52). CPU/memory table: partial. The founder stopped the device work before all 3 rounds finished, so n per mode is 1–3 (it is in the JSON). Runs whose journey stopped early (a tap on a notification banner) are excluded. Energy was not measured: xctrace's Power Profiler needs iOS 26.

G1: native crashes

Signals (SIGSEGV, SIGBUS, SIGABRT, SIGILL, SIGFPE, SIGTRAP, SIGSYS) and uncaught NSExceptions are written to disk at crash time by async-signal-safe C (OuoCrashCore), then sent on the next launch as a fatal exception of the crashed session, which ends with reason crash at the crash time (session-lifecycle spec, ADR-0004). ouo calls the previously installed handlers after its own, so Sentry still reports the crash. Simulator runs with crash-flow.sh against the env stack:

The JS fatal produced exactly one fatal exception (the JS one, with its JS stack); the native RCTFatalException report only set the end time (47 ms after the JS error).

ouo.crash.frames (instruction_addr, image_addr) and ouo.crash.images (code_file, debug_id = LC_UUID, image_addr, image_size, image_vmaddr) ride along as JSON so the stack can be symbolicated later (atos -o App.dSYM/… -l <image_addr> <instruction_addr>).

Limits and open points

  • Device numbers pending (above). The simulator overstates rendering, and other sessions shared the Mac during the runs.
  • Only the crashed thread's stack; no other threads. Crashes before initRUM, watchdog kills, OOM and SIGKILL are not caught in-process (MetricKit would be the next step).
  • The last replay chunk before a crash is in memory and is lost (Sentry keeps its segment on disk).
  • A crash within ~1 s of a new session can land before that session's session.start is exported; rum-api then reads the start from the first event.
  • The plugin does not read ouo.crash.frames / ouo.crash.images yet: they wait for symbolication.

Method

Simulator: iOS 27 "iPhone 18 Pro" (dedicated ouo-b1-ios), Release builds of examples/sentry-mobile with OUO_PERF=1, stack = ouo-env env b1-ios-replay-crashes. Time Profiler: 3 rounds per build interleaved, 80 s each (profile-runs.sh, attaching to the journey's pid). Sampler: scripts/perf/run.sh unchanged, 3 rounds × 3 modes per build. Crash flows: crash-flow.sh launches through a one-test XCUITest, which confirms iOS 27's "Open in …?" sheet for the deep link.
