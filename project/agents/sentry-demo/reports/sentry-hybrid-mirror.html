Verdict

Go, with conditions. The hybrid keeps production on its own path: in every run with tight mirror timeouts, production answered every request 200 whatever the bridge did (healthy, slow, refused, blackholed). The claim "a collector failure can only lose copies, never production data" is false with nginx's default timeouts: nginx reads a keep-alive connection's next request only when the mirror subrequest has ended, so a blackholed bridge held every device's next envelope for 60 s, 8 of 24 clients timed out, and 3 of those envelopes never reached production. It is true in effect with connect 50 ms / send 100 ms / read 100 ms: the worst case is then about +100 ms on a device's next request, and a dead bridge is free.

Three conditions: the mirror location's timeouts as below; passthrough_upstream unset on the mirror-fed bridge; one bridge instance (scale up, a backup standby), with key_from: x_forwarded_for and the fix in this PR so the rate limiter does not put every phone in nginx's bucket.

Do mirrors fire with upstream: none?

Yes, no change needed. answerLocally (receiver.go) writes and flushes the 200 {"id":…}, then calls mirrorEnvelope and enqueue, the same as forward does after the primary's answer. End to end: 60 envelopes through nginx → 60 accepted_local → 60 copies sent 200 at Preview; over the whole session 3 457 of 3 460 copies reached Preview (3 hit the 10 s mirror timeout while the sandbox Sentry's Kafka restarted).

1. Mirror latency coupling

A single fresh connection gets its answer on time even with a blackholed bridge (first byte 26 ms): nginx sends the production answer as soon as production answers. What it does not do is read the next request of that keep-alive connection until the mirror subrequest has ended. Sentry SDKs send their envelopes one after the other on a reused connection, so the mirror's time is added to the next envelope. Client-side latency, 8 keep-alive senders, production = stable sink:

What production received with nginx defaults and a blackholed bridge: 21 of 24 envelopes. 16 clients got their 200; 8 timed out after 60 s, and of those 5 had reached production anyway (the SDK will send them again: duplicates) and 3 had not (the SDK must retry them, if it kept them). With 100 ms or 500 ms timeouts every request got its 200 in every scenario.

Copy loss with 100 ms. 0 of 400 at 40/s on a healthy bridge. At 32 unpaced senders (~70/s) on the saturated host 128 of 1 200 copies (11 %) hit the read timeout: the bridge's answer took over 100 ms under that CPU load. Lost copies are visible only in nginx's error log (upstream timed out … subrequest: "/_ouo_mirror"); nginx does not log subrequests to an access log.

Recommendation. proxy_connect_timeout 50ms; proxy_send_timeout 100ms; proxy_read_timeout 100ms; proxy_next_upstream off; on the mirror location; the bridge next to nginx (same host or pod), so a dead bridge refuses at once; upstream keepalive 16; keepalive_timeout 30s; (below the collector's 1 min idle timeout: with both at 60 s nginx reused a just-closed connection 3 times, upstream prematurely closed connection); mirror_request_body on (without it the bridge gets an empty body) and client_body_buffer_size 1m so bodies stay in memory. Raise the read timeout only if the copy loss in nginx's error log is too high; every millisecond of it is what a stalled bridge can add to a device's next request.

2. Duplicates with passthrough_upstream

Yes, copies reach production a second time. In code: a known project with upstream: none is answered locally and never forwarded, but every request the table does not match goes to passthrough_upstream (unknown key or project, other paths, non-POST; receiver.go handle). Behind a mirror, that is every envelope of the other apps that share the production ingest host. Test: 60 envelopes of the bridge's project and 60 of another project through nginx. Passthrough unset: production received 120 (bridge: 60 accepted_local, 60 rejected auth, answers ignored by nginx). Passthrough = production: 180 (61 passthrough, the 61st my readiness probe on /). Sentry drops a repeated error event id, but sessions, transactions, replays and attachments count twice and spend quota twice.

Validation? No. A bridge at the edge with upstream: none (the cutover mode) needs passthrough to keep unknown DSNs alive, and the receiver cannot tell that it is fed by a mirror. The rule is now in the spec (section 2a) and the deployment guide's hybrid section: a mirror-fed bridge leaves passthrough_upstream unset.

4. Scaling several bridges behind the mirror

  • hash $remote_addr consistent: correct only while a device keeps its address. A phone moving Wi-Fi ↔ cellular mid-session continues on another instance from that envelope on (the rest of the session is "none"-matched, the replay drops segments). Carrier NAT puts many phones on one address: grouping stays correct, load is uneven. consistent limits reshuffles to about 1/N of the keys when an instance is added or removed, but each reshuffle splits the sessions it moves.
  • Hash on X-Forwarded-For: the same as $remote_addr when nginx is the edge; useful only with a load balancer in front of nginx. The client can also set the header, so only the hop your own balancer added is trustworthy.
  • Hash on the DSN key ($http_x_sentry_auth): correct, but one app's traffic is one instance: it scales across apps, not within one.
  • Device or session id header: Sentry SDKs send none (request headers are X-Sentry-Auth, User-Agent, Content-Type, Content-Encoding); the device and session ids are inside the (often gzip) body, out of reach for a plain nginx hash. An app-set transport header would work but needs an app release and is unverified per SDK.
  • ouoratelimit key_from: x_forwarded_for: did not work for bridged telemetry before this PR. The receiver handed its output on with client.Info.Addr = the TCP peer (nginx) and no metadata, so the limiter fell back to nginx's address and every phone shared one 100/s bucket. Fixed here: the request's X-Forwarded-For goes into client.Info.Metadata (TestForwardedForReachesThePipeline, fails without the fix). Through nginx with 20 device addresses and key_from: x_forwarded_for: 1 200 envelopes, 0 ouo_ratelimit_rejected, 0 translate drops. The same run with key_from: address could not be repeated on the saturated host (not re-measured); the 2026-11-15 one-address measurement dropped 1 223 / 398 / 501 logs / traces / replay batches out of 600 envelopes.
  • Rolling restarts: while the bridge restarts (3.2 s measured on 2026-11-15) the mirror gets refused connections, which cost the device nothing with the timeouts above; the copies of that window are lost for Preview and ouo, and the restarted instance rebuilds session state from the next envelopes. With an nginx backup standby the copies go to the standby, whose state is cold: same effect, shorter gap.

Recommendation: one instance, scaled up, with a backup standby. Measured on this shared, overloaded Mac: lossless at 40 envelopes/s with the 100 ms read timeout (0 of 400 copies lost; 3 457 of 3 460 Preview copies over the session); 11 % of copies lost at ~70/s from 32 unpaced senders at host load 18–28. The CPU-bound ceiling of one bridge on the same Mac was ~300 envelopes/s at 130 % CPU (2026-11-15, forwarding mode, which also does the round trip to Sentry). So one instance is enough up to ~40 envelopes/s measured lossless here, and up to about 300/s by the earlier CPU ceiling, the latter to be re-measured on the target VM with a dedicated core and the pilot's real envelope rate (from production Sentry's accepted-outcomes stats) before go.

Recommended nginx snippet

upstream ouo_bridge {
    server 127.0.0.1:4320;                # the bridge next to nginx: a dead one refuses at once
    server ouo-bridge-standby:4320 backup;
    keepalive 16;
    keepalive_timeout 30s;                # below the bridge's idle timeout (1 min)
}
server {
    # ... the existing listen / ssl / server_name and location / { proxy_pass <production> } ...
    client_body_buffer_size 1m;           # the mirror needs the body; keep it in memory
    location ~ ^/api/[0-9]+/envelope/$ {
        mirror /_ouo_mirror;
        mirror_request_body on;           # required: the bridge needs the body
        # ... the same proxy_pass and headers to production as location / ...
    }
    location = /_ouo_mirror {
        internal;
        proxy_pass http://ouo_bridge$request_uri;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 50ms;
        proxy_send_timeout 100ms;
        proxy_read_timeout 100ms;
        proxy_next_upstream off;
    }
}

Bridge side: upstream: none, the Preview mirror with its own sentry_project_id and public_key, no passthrough_upstream, ouoratelimit client.key_from: x_forwarded_for. Same text in docs/sentry-bridge-deployment.md, section "Hybrid".
