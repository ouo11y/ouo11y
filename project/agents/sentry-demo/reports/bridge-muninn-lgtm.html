Answer

Yes, with one exception: replay. Errors, crashes, sessions, logs, breadcrumbs, mobile vitals (Loki), transactions (Tempo), span metrics and the bridge's own counters (Mimir) and spec-wire replay (Muninn) all flow through one collector config at once. Bridged replay does not reach Muninn: the bridge emits the MVP video chunk, which Muninn's wire does not accept and ADR-0019 forbids translating in the collector. In this stack bridged replays go to rum-api, where today's plugin plays them. A down Loki, Muninn or rum-api never slowed the bridge's answer to the SDK.

What made it possible: the --muninn collector config on main had no bridge at all (port 4320 was published and advertised, nothing listened). deploy/compose/collector/config.muninn-sentry.yaml is now merged over config.muninn.yaml (two --config flags), so one collector runs both paths:

Sentry bridge :4320 (unchanged Sentry SDK)logs/sentry (limiter, project stamp) → routing/sentry: video chunk → ouoreplay → rum-api; everything else → the same logs pipeline → Loki. Transactions join the traces pipeline → Tempo → span metrics → Mimir.
Sentry itselfThe bridge forwards every envelope byte for byte and answers with Sentry's answer (or answers locally with upstream none, as here); translation runs afterwards on its own workers. The sibling session's fan-out work is not part of this stack.

Before the production cutover

The rate limiter will drop ouo's copy of most bridged traffic behind a reverse proxy. The bridge hands the pipeline a client context with the TCP peer address and no request metadata (translate.go:915, replay.go:444 in ouosentryreceiver). ouoratelimit's client key reads X-Forwarded-For from that metadata (OUO_RATELIMIT_CLIENT_KEY=x_forwarded_for, set on the VM) and falls back to the address, so behind Caddy every phone shares one client bucket: 100 calls/s, burst 300, and an envelope costs one to three calls (logs, traces, replay). Measured from one address: all 600 envelopes answered 200 (Sentry gets everything), but ouo_sentry_translate_dropped_total rose by 1 223 logs, 398 traces and 501 replay calls, and only 14 to 23 of 40 sessions reached Loki per phase. With the limits raised: 40 / 40 in every phase.

Options: (a) the receiver copies X-Forwarded-For into client.Info.Metadata (receiver code; left to the session that owns it); (b) for tomorrow, raise OUO_RATELIMIT_CLIENT_RATE / _BURST on the VM, or take ouoratelimit out of the bridge's logs pipeline, since Sentry's own answer already throttles the SDK. Size OUO_RATELIMIT_PROJECT_RATE (1 000/s, burst 5 000 per project) against the app's peak envelopes per second times about two. Alert on ouo_sentry_translate_dropped_total and ouo_ratelimit_rejected_total.
Loki's 4 MiB gRPC limit breaks session lists at bridge volume (fixed here). After the load runs (a few thousand bridged sessions), rum-api's session list, one Loki query of up to 5 000 lines, hung for 60 s and the plugin's Sessions page failed. Loki's log: received message larger than max (5306405 vs. 4194304): the querier could not hand a 5.3 MB split back to its frontend, because a bridged mobile record carries about 1 KiB of structured metadata. deploy/compose/loki/config.yaml (and the Helm chart's Loki configmap, which mirrors it) now raises server.grpc_server_max_{recv,send}_msg_size and frontend_worker.grpc_client_config.max_send_msg_size to 64 MiB: the same query answers 200 in 1.0 s, and a 24 h session list in 1.7 s. The VM install uses this file, so production needs it too; any reader that asks Loki for thousands of lines (the BFF readers in ouo-go) hits the same wall without it.
Open PR ouo11y/ouo11y#208 (remove rum-api) makes config.yaml the spec wire plus the bridge, as here, but routes bridged replay segments to the debug exporter: once it merges, Sentry replays are stored nowhere until the plan below lands. It also deletes compose.muninn.yaml, which makes this change's overlay moot (nothing to merge by hand: drop the overlay file).

Why the answer cannot wait on a backend: the bridge answers (or forwards to Sentry and copies its answer) first, then puts the envelope on a bounded in-memory queue with a non-blocking send (receiver.go enqueue: full queue = counted drop queue_full). Translation runs on its own workers; a pipeline error is a counted drop (consumer_logs, consumer_traces, consumer_replay). The latency spread between phases is the Mac's load (a self-hosted Sentry ran next to it), not the outage: the slowest phase is the one that also pushed 50 MB through fsync.

Limits of this test. Each outage lasted 1 to 2 minutes. The LGTM exporters keep an in-memory queue (1 000 batches) and retry for 5 minutes, and ouoreplay the same: a longer Loki or rum-api outage, or a collector restart during one, loses that data (Sentry keeps it when the bridge forwards). Only Muninn's spec-wire queue is on disk. Bridged replays can never use the disk queue's back-pressure: the SDK already has its 200 before the queue is written (spec COL-4 cannot hold for the bridge).

Plan: bridged replay into Muninn

Scoped, not built here: it is receiver Go code, owned by the session working on the bridge, and ADR-0019 already decided the direction ("a Sentry receiver for the spec wire is built with the others"). About one session of work for steps 1 to 4.

  1. Receiver emits ouo-video/1 (replay.go emitReplay), as mobile-replay.md defines it for the RN SDK: scope ouo.replay, event_name ouo.replay.chunk, body = one JSON header line (t, type: "video", end, w, h, scale, fps, frames, mp4 length, touches), a newline, the mp4 bytes. Attributes: session.id as 32 lowercase hex (Muninn's syntax; today the bridge keeps Sentry's dashed uppercase sid, so the session id differs between Loki and Muninn unless both change together), ouo.replay.id = Sentry replay_id, ouo.replay.stream.id = a deterministic hash of the replay id (retries must give the same identity: MUN-13 dedupes), sequence and segment.index = segment_id, keyframe true, start_time / end_time, format ouo-video/1, encoding identity, sha256, byte_size (over 1 MiB: drop and count), masked, mode from replay_type (buffer with trigger error), ouo.replay.source.vendor sentry, source.id the replay id.
  2. End records: on a session's exited / crashed / abnormal update, emit ouo.replay.ended (partial unless every segment up to the last was emitted) so Muninn can mark the stream finished.
  3. Config: logs/sentry exports to routing/replay (a connector can be the exporter of several pipelines), and routing/sentry, ouoreplay and the debug sink go. The reference copy in Loki then comes for free (COL-6).
  4. Tests: receiver unit tests check every attribute against Muninn's rules (section 3) and that a retried segment gives the same bytes; the golden test's expected output changes; sentry-demo.sh checks Muninn's manifest per replay (20 segments, the mp4 after the header equal to the SDK's by sha256) instead of rum-api.
  5. Reader (separate, plugin side): @ouo11y/kit lists ouo-video/1 as "the video player is not wired to ouo-video/1 yet"; the same player serves the RN SDK's video, so this is shared work, not bridge work.

Accepted limit: the bridge cannot give the SDK Muninn's back-pressure (503 on a full queue), because Sentry's answer is what the SDK gets. A full replay queue is a counted drop, and Sentry still has the segment when the bridge forwards.

What is missing

  • Bridged replay in Muninn (plan above). After PR #208 merges, bridged replay is lost until then.
  • Bridge client key behind a proxy (urgent box above).
  • Disk-backed queues for Loki and Tempo: in memory today, as in config.yaml.
  • Android Sentry traffic: only iOS goldens exist; Android payloads are still unverified (bridge spec status line).
  • Session id spelling: Sentry's dashed uppercase sid in Loki vs. Muninn's 32 lowercase hex; settle it with step 1 of the plan.
  • ouo-env up fails while the shared Traefik's 3 s health check times out on a loaded Mac; the stack was started with the exact compose command ouo-env generated.
