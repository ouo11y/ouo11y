What the founder can say

Claim (safe to say, with the caveats): "We measured a React Native demo app that already runs Sentry with tracing, logs and Session Replay. Adding the ouo SDK with ouo replay off (the default) made no difference to CPU or memory that we could tell apart from run-to-run noise: CPU changed by +0.1 percentage points of one core (from 15 %; the range over six paired runs was -0.7 to +0.8), memory by +0.6 MB (on about 60 MB), app start by +2.5 ms (noise is about 50 ms either way), and JavaScript frame drops did not change. What ouo does add is network traffic: about 15 more requests and about 60 KB more upload per 95 seconds of active use (about 2 MB an hour), next to about 650 KB from Sentry. Only one SDK should record the screen: turning ouo replay on as well added about 7 points of CPU, about 1 MB of upload per 95 seconds and about 0.1 s to app start. These numbers come from the iOS simulator on a Mac, one demo app, release build; a phone will show different absolute values, so we quote the differences."

Findings

  • ouo next to Sentry, replay off, costs nothing measurable on the device, except network. Paired by round (each round runs every mode back to back), Sentry + ouo minus Sentry only: CPU +0.1 pp (range -0.7 to +0.8), idle CPU 0.0 pp (-0.5 to +0.6), steady memory +0.6 MB, start +2.5 ms (-50 to +26), JS frames dropped +1 (-5 to +3), long frames -1. All inside the spread of Sentry-only runs against each other.
  • Network is the cost of ouo with replay off: 15 more requests per run (ouo's OTLP exports, batched: 78 instead of 63), +59 KB uploaded per run (median; ouo's OTLP traces and logs are 53 KB of it, the rest is the extra traceparent / baggage headers on every API call: 21.4 KB of backend requests instead of 18.7 KB), +1.5 KB received. Per hour of foreground use: about 570 more requests and 2.2 MB.
  • For scale, Sentry itself (tracing, logs, Session Replay at 100 %) against the same app with no SDK: CPU +9.6 pp, idle CPU +7.4 pp, steady memory +8 MB, peak memory +56 MB (its replay video pipeline), start +141 ms, 38 requests and 651 KB uploaded per run.
  • Two screen recorders is the expensive case. ouo replay on next to Sentry's: CPU +6.6 pp (+4.4 to +7.5), idle CPU +5.0 pp (replay keeps capturing with nobody touching the app), start +93 ms, upload +1.08 MB per run (11 replay chunks, about 40 MB per hour with masking off), memory +1 MB. ouo replay alone (no Sentry) costs about the same against no SDK: +7.2 pp CPU, +10 MB peak, +99 ms start, 1.2 MB per run.
  • Main-thread stalls (one Instruments Time Profiler run, Sentry + ouo with ouo replay on, symbolicated with the dSYM). Native Sentry code was 33 % of the app's sampled CPU (mostly SentryGraphicsImageRenderer, SentryFileManager.write, redaction) and ouo's ReplayRecorder.captureFrame 27 %; both run on the main thread. Each ouo frame capture held the main thread for about 49 ms (median of 89 captures, p95 52 ms, max 58 ms), about three 60 Hz frames once a second; Sentry's captures held it 18.5 ms (median of 150, p95 41 ms). The JS frame monitor does not see this (it watches the JS thread). The simulator renders on the CPU, so a phone will be faster, but this is the first thing to check on a device before turning ouo replay on in an app that already records with Sentry, and a lead for ouo replay itself (move scaling and encoding off the main thread).
  • Simulator-only effects kept out of the numbers above: 2 to 5 s at about 100 % of a core before main() (dyld_sim, same for every mode, so CPU and start are counted from JS start), Sentry's replay video encoded by the simulator's software H.264 codec (H264SW.videocodec; a phone has a hardware encoder, so Sentry's own replay CPU is overstated here), and XCUITest's accessibility work inside the app (XCTAutomationSupport, UIAccessibility: about 8 % of sampled CPU, the same in every mode).

Caveats

  • No real device was available (xcrun devicectl list devices lists simulators only). iOS 27 simulator, iPhone 18 Pro profile, Apple M5 Mac, 10 cores, 32 GB. Absolute CPU %, memory and start times will differ on a phone; the differences between modes are the result.
  • One app: examples/sentry-mobile (3 screens, about 25 API calls per run). An app with more requests or more log lines sends proportionally more OTLP data through ouo.
  • Masking is off in both SDKs (demo setting). Masking adds a view-tree walk per frame to each recorder.
  • Sentry is configured at 100 % sampling for traces and replay (the demo). With lower sample rates Sentry costs less and the "two recorders" case happens less often.
  • 95 s runs, 6 per mode, interleaved. Rounds 5 and 6 ran on a quieter host (every mode cheaper; process start to JS start 1.8 s instead of 3.4 s). Medians per mode are shown with the full range; the deltas above are paired within a round, which cancels that drift.
  • Network bytes are HTTP level on plain HTTP to localhost; TLS and TCP/IP overhead come on top in real use (the same for every mode). Energy is the host kernel's estimate for a Mac process, not a phone battery reading.
  • Main-thread stall numbers come from one Time Profiler run; the other metrics from all 30 runs.
