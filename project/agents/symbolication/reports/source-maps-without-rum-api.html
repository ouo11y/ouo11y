Source maps without rum-api

Where source-map storage and stack-trace lookup live once services/rum-api is removed. Design with a working prototype for the web, 2026-11-13. Proposed as ADR-0022.

Recommendation

Uploaded source maps become write-once files in Muninn, keyed by tenant, project and debug id, opaque to Muninn. The ouo-sourcemaps CLI keeps its request and sends it to a small upload route on the Collector, which passes the file to Muninn and returns Muninn's answer. A library in ouo-go resolves a stack when the BFF serves an error, with a cache of parsed maps. A frame finds its map by debug id; a frame without one uses release and path only when exactly one build matches.

The prototype does this end to end with a real minified build and a real stack from @ouo11y/browser 0.4.0. The CLI needed no change to upload.

The options

(a) Where the files are stored

OptionForAgainst
Muninn, as a second object kindOne owner of the bucket: tenancy, retention, delete-by-project and credentials exist once. Same write-once rule as replay chunks. The BFF already has a Muninn clientMuninn's spec grows by one prefix and three routes
The BFF's own bucket prefixNo change to MuninnTwo owners of the bucket. CI would have to reach Grafana, or the Collector route needs bucket access
Keep a small symbolication serviceNo design changeKeeps the service that was decided away, for about 1,600 lines that fit a library

(b) How they are uploaded

OptionForAgainst
A pass-through route on the CollectorThe Collector stays the only edge. CI gets Muninn's real answer, so a failed upload fails the build. The CLI keeps its requestOne small custom Collector component
OTLP log records through the stock pipelineNo custom component; the path replay chunks takeThe Collector answers 2xx when a record is queued, not when it is stored, so CI cannot tell. The receiver caps a request at 20 MiB by default, so dSYMs need chunking
CI straight to MuninnNothing to build; what rum-api has todayOnly works when CI is inside the operator's network. Acceptable as a first step (decision D2)

(c) Where and when a stack is resolved

OptionForAgainst
ouo-go in the BFF, on readA map uploaded after the error still applies. The Collector stays stateless. The record in Loki stays as sent. Cost is one parse per map per processLoki cannot be searched by original file name. The BFF holds parsed maps in memory
At ingest, in the CollectorResolved names in Loki; what Sentry, Datadog and PostHog do, because they group errors into issues at ingestLate uploads never apply. The Collector needs bucket access, a map cache, and parses on the ingest path. ouo has no issue grouping yet; it can be added later with the same library

(d) How a frame finds its map

OptionForAgainst
Debug id; release + path only when exactly one build matchesA debug id names the exact bytes. Never shows a confident wrong line. Bundles that cannot run inject still workOne pointer object per map for the fallback
Release + path onlyNo inject stepTwo deploys of one version, and every over-the-air React Native bundle, share a path. rum-api already mapped one bundle with another's map this way
Debug id onlySimplestBuild tools that cannot run the inject step get nothing

  • Memory. A parsed map keeps about twice its decompressed size on the heap (64.5 MB for 33.6 MB), mostly the embedded sources. Peak process memory while parsing the 33.6 MB map was 167 to 212 MB (3 runs, each parsing it twice, store in the same process); 24 MB for the 1.12 MB map (3 runs).
  • Storage. gzip keeps 22 to 26% of a map. One ouo-web release is 424 KB on disk with meta and pointers.
  • Missing map. 0.27 ms cold (one 404 from the store), 0.03 ms once the miss is remembered (median of 30). The stack comes back as recorded.
  • "Frame made up" means the stack is one frame placed in the middle of the bundle's longest line, because no real error was thrown in that bundle. The 1.12 MB row is the real captured stack.

Not measured

  • S3 or MinIO instead of the filesystem: a cold map adds one object GET.
  • A real Collector in front of the store. The upload route is a stand-in in the prototype.
  • A React Native app on a device. The Hermes case uses rum-api's fixture, built by Metro and hermesc.
  • dSYMs and R8 mappings in the new store. They are design only.
  • Ingest-time resolution was not built: it uses the same library, so its per-error cost is the warm and cold numbers above. What separates the two options is behaviour (late uploads, state in the Collector), not speed.

The three inputs

InputKeyState
Web source mapsDebug id from ouo-sourcemaps injectPrototyped and measured
React Native (Hermes) mapsDebug id from the Metro plugin, read from the bytecode at uploadResolver verified on the Hermes fixture; build tooling unchanged from ADR-0011
iOS dSYMThe image's LC_UUID, already in every crash reportDesign: kind dsym in the same store; the DWARF reader moves from rum-api. The CLI splits universal files itself
Android R8 / ProGuard mappingA UUID made from the mapping file, written into the app at build timeDesign: kind proguard; the retrace resolver is new work

Decisions for the founder

#DecisionRecommendation
D1Does Muninn hold debug files, as a second object kind with three routes?Yes. The fallback is the BFF's own bucket prefix with the same layout; the ouo-go code is the same either way
D2Upload path for the pilot: the Collector route now, or CI straight to Muninn until it exists?Build the route together with Muninn's debug-file routes. Direct upload only if the pilot's CI is inside the network
D3Keep the release fallback?Yes, with the exactly-one rule
D4Retention default for debug filesOne year from upload, per-project override, 0 keeps forever
D5Resolve on read only, or also at ingest?On read only until issue grouping exists
D6Order of native workdSYM moves with the JavaScript code; R8 retrace after web and React Native are live
