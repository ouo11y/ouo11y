1. Duplicate session.start on expired-session rotation (bug)

Where
sdk/browser/src/session/manager.ts (start(), ensure(), end(), create()) and sdk/browser/src/telemetry/correlation.ts (log processor calls session.id() for every record).
Observed
Two session.start log records with different session.id, identical timestamp and the same session.previous_id, each time an expired session is found at init. One id is persisted to localStorage and used by the page; the other never gets another event. rum-api lists it as a separate healthy session with event_count=1, no traces, no replay, which inflates the healthy count and the totals on the Overview page.
Reproduced
2 of 2 attempts in the web demo (real @ouo/browser, Vite dev server): rotation of 52f6ac9e-... produced 4a9c76df-... (kept) and fb2fe879-... (phantom) at 21:35:15.765Z; rotation of 4a9c76df-... produced 071a0ed0-... (kept) and add731c5-... (phantom) at 21:39:41.904Z. Exactly one session.end (reason inactivity) was emitted for the old session each time, so the end path is fine.
Cause (from reading the code)
end() sets this.current = null and then emits session.end through onEvent. The event goes through the OTel log pipeline, where SessionLogProcessor computes sessionAttributes(session) and calls session.id() -> ensure() -> current is null -> create(now): first session.start (phantom, but persisted for a moment). Control returns to start() (or to ensure() after its own end() call), which calls create(now) again: second session.start, which is the one that wins because it is persisted last. The record already carries session.id so the processor keeps the old id on the session.end record, which is why the end looks correct. The same re-entrancy exists for the same-tab inactivity timer and for the lazy restart after a max-duration end (ensure() path).
Repro steps
# web demo running at http://localhost:5173 with the real SDK
# in devtools on the page:
const o = Storage.prototype.setItem;
const rec = JSON.parse(localStorage.getItem('ouo.session'));
rec.lastActivity = Date.now() - 31 * 60 * 1000;
Storage.prototype.setItem = (k, v) => { if (k === 'ouo.session') return; return o.call(localStorage, k, v); };
o.call(localStorage, 'ouo.session', JSON.stringify(rec));
location.reload();
# then (ports from deploy/compose/.env)
curl -sG localhost:3101/loki/api/v1/query_range \
  --data-urlencode 'query={service_name="web-store", event_name="session.start"} | session_previous_id="<old id>"' \
  --data-urlencode "start=$(( $(date +%s) - 600 ))000000000" --data-urlencode "end=$(date +%s)000000000" \
  | jq '.data.result[] | [.values[0][0], .stream.session_id]'        # two rows instead of one
Status
Fixed 2026-10-08 (sdk-browser, see project/agents/sdk-browser/summaries/2026-10-08-bugfix.md): the manager now installs the replacement session before emitting session.end / session.start (rotate()), and SessionLogProcessor no longer calls session.id() for records that already carry session.id. Live re-check: rotation of 071a0ed0-... produced only 98143ee0-...; Loki shows one session.start with that previous_id and one session.end (end_reason=inactivity). sdk/react-native was not affected (its processor already used peek()).
Suggested fix
Make create() / ensure() re-entrancy safe: for example set this.current to the new record (or a "creating" guard) before emitting session.end, or have the log processor skip ensure() when the record already carries session.id (compute sessionAttributes lazily). Add a unit test asserting exactly one session.start per rotation with the real processor chain (the jsdom integration test only covers a fresh init). Check sdk/react-native's manager for the same pattern (cold start with an expired persisted session, background rotation).

2. Trace ids without leading zeros (minor)

Observed
Tempo 3.0.3 /api/search returns traceID with leading zeros stripped (e.g. 0a092857191aec6d753aba594dae8cbd comes back as a092857191aec6d753aba594dae8cbd). rum-api copies it into traces[].trace_id and the grafana_url; the plugin shows the short id and copies it to the clipboard. Grafana Explore shows the full id in the trace header, so the link works. Not an error, but the displayed id is not the W3C 32-hex form and would not match a value copied from a client log.
Repro
deploy/scripts/e2e.sh prints short_trace_ids in its --out JSON whenever one of the checked sessions has such a trace (about 1 in 16 ids start with 0). Suggested: left-pad to 32 in services/rum-api/internal/tempo.

3. Timeline tie-break (minor)

Observed
In every web session the first two timeline rows are navigation (load) then session.start, both at the same millisecond (the SDK emits both at init). Suggested: when timestamps tie, order session.start first and session.end last in services/rum-api/internal/session.

4. ended_at vs ouo.session.ended_at (minor)

Observed
Session 52f6ac9e: the SDK's session.end record carries ouo_session_ended_at=1791408855722 (21:34:15Z, lastActivity + 30 min) and ouo_session_duration_ms=93252, but rum-api reports ended_at=2026-10-07T21:35:15.765Z (the record's timestamp, i.e. when the next page load detected the expiry) and the plugin shows "Ended 00:35:15, Duration 2m 33s", which do not agree with each other. Suggested: prefer the ouo.session.ended_at attribute when present.
