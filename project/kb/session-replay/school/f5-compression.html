Fundamentals

Compression basics, and how H.264 skips

Replay data is either text (JSON events, wireframes) or images (JPEG, WebP, video). Text shrinks well with general-purpose compression; images are already compressed and need a different trick: send only what changed. This lesson shows four mechanisms, from gzip to the H.264 skip block.

Builds on: Keyframes and deltas

The mechanisms on this page are general facts from the published standards (linked in each section), not read in any vendor's code. Vendor-specific numbers are linked to the vendor source or the Step 6 measurements.

1 · Text: deflate finds repeats

gzip and zlib are wrappers around deflate. Deflate does two things: it replaces a run of characters that already appeared by a back-reference (go back d characters, copy n), and it gives frequent symbols shorter bit codes (Huffman coding). Replay JSON is full of repeats, {"id":, "type":, the same tag names, so it shrinks a lot. Press ▶ to watch the back-references being found.

Greedy matching of length 4 or more over the whole string, computed live; real deflate limits the window to 32 KiB and lengths to 258, and then Huffman-codes the result. Illustrative tokens, not a byte-exact stream. Standard: RFC 1951 (deflate), RFC 1952 (gzip), RFC 1950 (zlib).




Two vendor details that only make sense with this picture. Sentry compresses as events arrive in a worker, one zlib stream per upload, so flushing only has to close the stream. Datadog sends each reply with a ready-made stream ending, so a closing page can finish the stream without waiting for the worker (Sentry on the web, Datadog on the web).



2 · base64 costs a third, and gzip cannot win it back on images


JSON cannot hold raw bytes, so images inside JSON are written as base64: every 3 bytes become 4 characters from a 64-letter alphabet.








Standard: RFC 4648 §4.




So base64 makes a picture 4/3 as large. A JPEG or an MP4 is already compressed: its bytes look random, deflate finds almost no repeats, and the third stays. This is why the draft spec labels JPEG and MP4 chunks encoding: identity and carries the bytes raw in an OTLP protobuf body (lesson How to pack, choice 1).



3 · Pictures: send only the parts that changed


A picture recorder cannot diff text, but it can diff areas. Two ways are in use. ouo's mobile frames cut the image into 64 px tiles, hash each one against the last frame sent, and send nothing, a few changed tiles as JPEG patches, or a full JPEG when more than half changed (mobile-replay spec, capture rule 6). A video codec such as H.264 does the same at a finer grain, inside the encoder.


The demo draws two real frames and compares them, pixel by pixel. Pick what the user did between the frames, then switch between the two ways of looking at the change.

Not to scale: tiles are drawn as 45 px and blocks as 15 px on a 180 px wide screen, standing for 64 px tiles and 16×16 blocks of the real image. Block decisions are computed by comparing the two frames, with one candidate motion (the scroll offset). A real encoder searches many vectors, can split a block down to 4×4, and can code any block from scratch even in a P-frame.





4 · H.264: I-frames, P-frames and the skip block


    

  • The encoder cuts each frame into 16×16-pixel macroblocks.
    • 

  • An I-frame (key frame) codes every block from the frame itself. It can be shown alone.
    • 

  • A P-frame codes each block as a reference into the previous frame. A block that matches it is a skip: no pixels, signalled in about one bit. A block whose content moved costs a short motion vector plus a small correction (the residual). Only blocks with new content cost real pixels.
    • 

  • So an unchanged frame is a few dozen bytes, and a scroll is mostly motion vectors: this is where video beats tiles, since every tile changes when the list moves.
    • 



Sentry's mobile recorders use this: 1 fps H.264, no B-frames, a key frame at least every 6 frames (MaxKeyFrameInterval = 6), and each 5 s segment is its own MP4 that starts with one (SentryOnDemandReplay.swift L381–440). So a static screen still costs one full picture per segment; Step 6 measured about 36 KB per idle 5 s segment on Android (mobile-replay-evidence.md).


Standard: ITU-T H.264 (macroblocks, P slices, mb_skip). Read from the standard's concepts, not from any encoder's code.


Packing never changes what the replay shows or whether masking is right; it only changes bytes and CPU. That is why the course treats "tiles or video" as an optimisation, and spends its design attention on what to record and how to mask.
