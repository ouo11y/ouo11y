Fundamentals

Pixels versus structure

Session replay writes a screen down so it can be shown again later. There are only two ways to know what is on a screen: read a description of it, or look at its pixels. Every technique in this course picks one, or mixes both.

Picture a shopping-cart screen: a heading, two items with prices, a toggle, a chart someone drew by hand, and a pay button. A recorder that wants to replay it later has two options.

  • Structure: ask the UI framework what it is showing. "A text that says Tea at x 12, y 58. A toggle, switched on." The answer is a tree of objects with types, text and positions.
  • Pixels: copy the colours of the screen. "Pixel (12, 58) is dark grey." The answer is an image. It shows exactly what the user saw, but it does not know that the dark pixels spell a word.
One screen, two ways of knowing it. Press a button and watch what the recorder learns.
Pick a way of knowing the screen.
On the device
What the recorder now knows







The one idea to keep: on the web the browser hands any script a live, readable, observable tree (the DOM) that fully describes the page. On mobile there is a tree too, but it is private to the app's UI framework, it is not the whole truth (custom drawing, SwiftUI, Compose and Flutter hide inside one view), and nothing notifies you when it changes. That single difference explains why web replay is a text diff and mobile replay is mostly pictures.

Real recorders come in four families, and they sit on this line: tree + diff (the web), wireframes (mobile structure, drawn as boxes), pictures (screenshots or video) and draw commands (record the drawing calls, not their result). Lesson What to record shows all four recording the same screen.
