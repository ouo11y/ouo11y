1 · Platform foundations: what is on the screen, and who knows about it

Every replay technique is an answer to one question: what does the platform let an outsider read about the screen, and when? So we start with how each platform turns a description of the UI into pixels.

The one idea to keep: on the web the browser hands any script a live, readable, observable tree (the DOM) that fully describes the page. On mobile there is a tree too, but it is private to the app's UI framework, it is not the whole truth (custom drawing, SwiftUI, Compose and Flutter hide inside one view), and nothing notifies you when it changes. That single difference explains why web replay is a text diff and mobile replay is mostly pictures.

1.1 The browser: the DOM, the event loop, and MutationObserver

The HTML parser builds a tree of nodes: elements (<ul>) with attributes (class="sel"), text nodes, comments. JavaScript changes this tree at any time. The browser does not repaint after each change: it batches them and, once per frame, runs style → layout → paint → composite. Between a script's task and the next frame, the browser runs microtasks, and that is where a MutationObserver receives a list of MutationRecords describing every change since the last delivery: childList (nodes added or removed), attributes, characterData (text).

What this gives a recorder for free:

  • A complete, serialisable description. Walk the tree once and you have everything needed to rebuild the page somewhere else, as text (this is the full snapshot).
  • A change feed. MutationObserver tells you exactly which nodes changed, asynchronously, batched, without polling (this becomes the incremental events).
  • Events on the same tree. Input, scroll, pointer, resize, visibilitychange, pagehide can all be listened to by any script.

What it does not give: pixels the DOM does not describe. A <canvas> or WebGL surface is one element whose content is a bitmap; a <video> is a URL plus a playhead; a cross-origin <iframe> is unreadable; the result of CSS from a stylesheet the recorder cannot fetch is lost. These are the "holes" of DOM replay.

Sources (specifications, the behaviour browsers implement): DOM Standard §4.3 Mutation observers (records are queued, then delivered in a microtask: queue a mutation observer microtask) · HTML Standard, event loop processing model (task, microtask checkpoint, then "update the rendering": rAF callbacks, style, layout, paint) · page visibility.

2 · Ideas behind capture: four ways to write a screen down

Topic 1 ended with a split: what you can read (a tree) versus what you can only see (pixels). Every replay technique sits somewhere on that line. There are four families, and each one answers "what do we write down?" differently:

  1. Serialise the tree, then diff it. Write the document structure as text once (a full snapshot), then write only what changed. The player rebuilds a real, live copy. This is rrweb, and every web recorder.
  2. Wireframes. Walk the native view tree and turn each view into a typed rectangle: text, image, shape, input, with position and style. The player draws rectangles that look like the app; it never rebuilds the real UI. Datadog, PostHog wireframe mode.
  3. Pictures: screenshots or video. Copy the pixels, paint boxes over private things, compress like images or like a movie. The player shows images. Sentry (video), PostHog screenshot mode, OpenReplay mobile, and ouo's current mobile SDK (JPEG frames with tile patches).
  4. Draw commands. Record the drawing instructions the UI issued (drawRect, drawText, drawImage) instead of their result. The player re-executes them. This is how rrweb records <canvas>, how Sentry Android's canvas strategy masks, and what Flutter's PictureRecorder produces internally.

    2. 

  2. What wakes the recorder? A change notification, a timer, a frame callback, a user event, a lifecycle event.
    3. 

  3. When is a capture not worth sending? Unchanged frames, throttles, idle back-off.
    4. 



A fourth question, when to send (flush), is closely tied to these and is covered in 3.4.



3.1 Keyframes and deltas, and why "checkouts" exist


A keyframe (rrweb: full snapshot; video: I-frame; ouo frames: full image) can be shown on its own. A delta (rrweb: incremental snapshot; Datadog: mutation / Change record; video: P-frame; ouo: patches) only means something on top of the frames before it. Deltas are small, but to show second 50 the player must load the last keyframe before 50 and apply every delta after it. If that keyframe is lost or far back, seeking is slow or impossible. A checkout is a keyframe taken on purpose, mid-session, to bound that cost and to let older data be thrown away (Sentry's error buffer keeps only what follows the last checkout).









Checkout rules in source: rrweb takes a full snapshot when checkoutEveryNth or checkoutEveryNms is reached, neither set by default (record/index.ts L220–241) · Sentry sets checkoutEveryNms = 60 000 in buffer mode (replay.ts L443–479) · PostHog web takes one every 5 min by timer (L1007–1042) · Datadog web on every RUM view, no timer (startFullSnapshots.ts L12–72) · Datadog iOS on a view id change (SnapshotProcessor.swift L99–127) · Sentry video: an H.264 key frame at most every 6 frames (SentryOnDemandReplay.swift L381–440) and every 5 s segment is its own MP4 · ouo frames: the first frame of every chunk is a full image, chunks cut every 5 s (mobile-replay spec).

3.4 When to send


Capturing and sending are separate decisions. Every SDK keeps captured data in a buffer and uploads it on one of four triggers. Time: Sentry web 5 s after the last event (at most 5.5 s), Datadog 5 s, PostHog 2 s, ouo mobile 5 s. Size: Datadog 60,000 compressed bytes, under the browser's 64 KB unload budget; PostHog about 0.9 MB; ouo 1 MiB of images. Lifecycle: tab hidden, page hide, app background. An error: in buffer mode Sentry keeps 30 to 60 s in memory and sends it only when an error happens. Lifecycle is the trigger that matters most, because it is the last moment the code is guaranteed to run. On the web after visibilitychange → hidden the tab may be killed without another event; on iOS, after didEnterBackground the app may be suspended within seconds.


The shape to remember: a change signal decides whether there is anything to capture, a clock decides how often at most, a hash decides whether it is worth sending, and the lifecycle decides when it must go out. The web gets the first for free (MutationObserver). Mobile SDKs approximate it with run-loop observers, draw listeners, swizzled layers or post-frame callbacks, then cap it with a clock.

6 · How ouo would ship it: every technique as an ouo.replay.chunk


The working assumption: whatever the capture technique, its output leaves the device as ouo.replay.chunk records, with the payload either in the record's body or held elsewhere and referenced. This topic shows what the repository already says, maps each technique from topics 2 to 5 onto that record, and lays out the choices still open. Evidence only: nothing here decides the format.



6.1 Two layers in the repo: what runs today, and the draft spec




Today (MVP-era code)

    

  • The SDK posts a gzip JSON chunk to POST /v1/replay/chunks on the Collector's ouoreplay receiver (port 4319): config.go.
    • 

  • Three kinds: rrweb (events), frames (JPEG full images and tile patches, base64 in the JSON: mobile-replay spec) and video (MP4 base64, made by the Sentry bridge from Sentry's replay_video: sentry-bridge spec §9–11).
    • 

  • The receiver validates the chunk and wraps the whole JSON as the bytes body of one log record, with session.id, ouo.replay.seq, ouo.replay.kind and ouo.replay.encoding = json: receiver.go (buildLogs).
    • 

  • The ouoreplay exporter posts the body on to rum-api, which stores one file per chunk; a session cannot mix kinds (409).
    • 



Draft spec (post-MVP Steps 2 and 3)

    

  • A chunk is an OTLP log record, event ouo.replay.chunk, scope ouo.replay, sent over OTLP/HTTP protobuf so bytes are not base64'd: sdk-spec.md §11, TRN-1.
    • 

  • Hierarchy session → replay → stream → segment → chunk; a segment starts with a keyframe and is decodable alone (RPL-6); each chunk body is independently decompressible, and a segment's bodies concatenated are a valid payload of ouo.replay.format (RPL-7).
    • 

  • Chunks close at 256 KiB compressed (hard limit 1 MiB), 5 s, stream end, or hide/background (RPL-10); a keyframe at least every 5 min and on visibility change (RPL-9).
    • 

  • Bytes to the Collector, then the Collector stores them and replaces the body with ouo.replay.ref (decision D3, recommended and applied, not yet decided): replay.md.
    • 

  • The format is pluggable and the mobile format is open (§11.6).
    •

What survives every option: the chunk record itself. Identity (session.id, replay, stream, sequence), the keyframe flag, the format and encoding labels and the hash are the same whether the body is rrweb JSON, wireframe records, JPEG tiles or an MP4. That is exactly what RPL-23 asks for ("the hierarchy, identity, chunk attributes, delivery and end rules MUST NOT depend on the format"), and it is why the mobile format can stay open while the transport is built.


One limit cuts across options 2 and 3: at page unload all keepalive requests share 64 KiB, and the draft spec keeps them under 60 KiB with telemetry first (TRN-16). A 256 KiB chunk cannot leave during unload; it stays persisted and a later page sends it (TRN-18). Datadog caps segments at 60,000 compressed bytes for the same reason (topic 4.5).

Why does H.264 encode an unchanged frame almost for free?

The encoder cuts each frame into 16×16-pixel blocks. In a P-frame (a frame stored as changes from the one before), a block that matches the previous frame is marked skip: about one bit, no pixels. A block that moved costs a short motion vector plus a small correction. So an unchanged frame is a few dozen bytes. The catch: Sentry iOS forces a full picture (key frame) at least every 6 frames (MaxKeyFrameInterval = 6), and every 5 s segment is its own MP4 that starts with one. So a static screen still costs one full picture per segment; Step 6 measured about 36 KB per idle 5 s segment on Android.


SentryOnDemandReplay.swift L381–440 · mobile-replay-evidence.md




When does ouo export frames?

A chunk closes at the first of: 5 s, 1 MiB of images, pause or background, a session rotation, a screen-size change. It is written to disk, then sent as its own request with retries. A chunk with no frames and no touches is not sent. The draft spec keeps time and lifecycle and lowers the size target to 256 KiB (hard limit 1 MiB).


mobile-replay.md · sdk-spec.md §11 (RPL-10)




Does Sentry drop frames in motion, or capture faster?

Neither. iOS keeps its rate during scrolling, waits (at most 1 s) while 4 or more animations run, and backs off to one frame per 2 s when a capture takes 150 ms or more. Android skips at most one frame that was drawn during the copy. Sentry trusts its timing; ouo refuses the frame. Neither has been measured for leaks: that is the masking-experiment session.

"My app moves much faster than once a second, yet Sentry replays look acceptable."

They are 1 fps. Two things hide it (reasoning, not measured): most app time is spent on still screens, where 1 fps loses nothing; and the player draws touches and navigation breadcrumbs from their own timestamps, so taps and screen changes look precise even though the pixels between them are one second apart. A fling or an animation does look like a jump.
