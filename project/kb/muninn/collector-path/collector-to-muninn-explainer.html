Collector to Muninn

How a replay chunk gets from an SDK into the replay store and back to a player. A proposal, 2026-11-11: ADR-0019 and the Muninn spec. Nothing here is built.

The path

A chunk is an ordinary OTLP log record: event ouo.replay.chunk, scope ouo.replay, the recording bytes as its body. It goes to the same endpoint as all other telemetry. The Collector separates it by scope name and nothing else in the stack needs a replay-specific wire format.

Who answers 2xx, and when

An SDK may delete a chunk only after a 2xx. So each 2xx on the path has to mean "this is on disk somewhere".

Hop 1SDK to Collector2xx after the chunk is written to the Collector's disk queue with fsync. The SDK deletes its copy.
Hop 2Collector to Muninn2xx after the chunk object is written to the object store. The Collector removes it from the queue.
Both hopsAt least onceA retry sends the same bytes. Muninn stores a chunk once, by its identity and SHA-256.

This works with stock Collector parts as long as nothing between the receiver and the queue returns early. The batch processor does, so the replay pipeline has none. What was checked in the Collector source and what still needs a test: durable-handoff.md.

Where a chunk lives

Object storage only, no database. One immutable object per chunk. The key starts with tenant, project and session, so "the replays of this session" is one prefix listing.

muninn/<tenant>/<project>/<session>/<replay>/<stream>/c/0000000042   chunk: header + body as sent
muninn/<tenant>/<project>/<session>/<replay>/<stream>/ended.json     the stream's end record
muninn/<tenant>/<project>/<session>/<replay>/<stream>/manifest.json  cache, rebuildable
muninn/<tenant>/<project>/<session>/<replay>/deleted.json            tombstone
Structure chunkPixel chunk
ContentWeb DOM recording, mobile wireframesJPEG frames and tiles, MP4 segments
Encodinggzipidentity, the codec already compressed it
Layout and containerThe same. Muninn never looks inside the body
Served withContent-Encoding: gzip, so the HTTP client inflates itByte ranges, so a video element can seek

Reading it back

Three calls, made by the BFF, never by a browser.

CallAnswer
GET …/sessions/{session}/replaysThe session's replays with state, time range and size
GET …/replays/{replay}The manifest: streams, chunks in order, keyframes, formats, missing sequences, and whether each stream is open, complete or partial
GET …/streams/{stream}/chunks/{sequence}The bytes as stored, cacheable for ever

The player picks a decoder by ouo.replay.format, starts each segment at its keyframe chunk and skips to the next keyframe after a gap. "Which sessions have a replay" is a Loki question, answered by the reference records.

Later, scoped but not designed

  • Vendor envelope receivers. One Collector receiver per vendor wire format (Sentry exists for mobile; Datadog and PostHog follow). Each turns the vendor's payload into OTLP for Loki, Tempo and Mimir, and its recordings into ouo.replay.chunk records that take the same route to Muninn. For Muninn a vendor recording is one more format value.
  • Vendor API querying is the BFF's. Muninn makes no outbound calls and holds no vendor credentials. A Sentry reader is a library in ouo-go, beside the Loki, Tempo, Mimir, Victoria and Muninn clients.
