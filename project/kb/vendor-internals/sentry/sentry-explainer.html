Sentry end to end

Step 6 of the post-MVP plan, researched 2026-11-10. Versions: @sentry/browser 11.11.0, sentry-cocoa 9.33.0, sentry-java 8.63.0, @sentry/react-native 8.34.0, self-hosted Sentry, Relay and Snuba 26.10.0. Every number here comes from the linked kb entries, where each claim has its source (code at a tag, docs, or an observed capture).

ouo rides on top of Sentry in three ways: (a) the Sentry SDK sends to Sentry and Muninn reads back through Sentry's API; (b) the Sentry SDK sends to our collector, which forwards to Sentry and keeps a copy; (c) our own SDK sends to us. This page follows one piece of data through every stage that matters for those three paths.

The whole path

Stage by stage

1. Browser SDK

In 11.x spans are sent by default as streamed span v2 items with typed attributes, not transactions, so beforeSendTransaction no longer runs. A replay segment is {"segment_id":N}\n plus a zlib stream. Client reports go out only on page hide. Closing a tab 300 ms after activity lost that segment. Errors only is 29.4 KiB gzip; adding tracing and replay brings it to 90.7 KiB.

browser-sdk/ · explainer

2. Mobile SDKs

On iOS and Android any HTTP 4xx or 5xx deletes the envelope; only network errors keep it, with no backoff timer. The disk cache holds 30 envelopes (a file count, not a byte cap). Replay is video segments; it pauses while offline or rate-limited, so the recording has a gap. In React Native, JS beforeSend never sees events the native SDKs create. Video replay (H.264, 1 fps, 5 s segments) measured 165 KB/min on iOS and 212 KB/min on Android with default masking.

mobile-sdks/

3. Relay (wire format)

Relay knows 23 item types. Only one event-like item fits in an envelope: an error plus a replay_event gets a 413 for the whole envelope. A gzip replay_recording body is accepted with 200 and then dropped silently. Two trailing newlines or CRLF line endings get a 400. Self-hosted does not scrub rrweb recordings for PII by default. Relay also takes OTLP traces and logs.

wire-format/ · explainer

4. Storage

Full events live in nodestore, which is a seaweedfs bucket compressed with zstd (the Postgres table is empty). Replay segments are files in filestore. Spans, logs and trace metrics share one ClickHouse table (eap_items_1_local). Sessions exist only as metric aggregates. Retention is 90 days here (SENTRY_EVENT_RETENTION_DAYS).

self-hosted-storage/

5. Read APIs (Muninn)

Four public replay endpoints: list, details, segment list, and per-segment download. The mobile video endpoint works but is experimental. Replays appear 2.4–5.4 s after the SDK sends them, errors after 5.5–7.6 s, spans after 14.5–18 s and sessions after about 50 s. There is no replay webhook, so Muninn must poll. Self-hosted applies no API rate limits.

Traps that cost us time

  • A 200 from Relay does not mean the data was stored. A gzip replay body (dropped with no outcome), a replay event without its recording (discarded as invalid), and a legacy user_report sent next to a feedback item all got a 200 and were not stored.
  • Replay recordings mix units: performanceSpan and ui.focus breadcrumbs use float seconds, everything else uses milliseconds.
  • The DSN public key shows up inside compressed replay network bodies (the baggage header), so redacting fixtures means decompressing them first.
  • A message event in 11.x carries a synthetic stack, so Sentry titled one message event "Of", the minified name of the function that sent it.
  • If the taskbroker consumer stalls, Relay answers 200 and holds the data until it is restarted (project/kb-archive/sentry-self-hosted.md).
