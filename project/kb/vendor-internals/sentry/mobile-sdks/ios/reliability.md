## 1. On-disk layout

`<cacheDirectoryPath>` defaults to the app's `Library/Caches` ([Options.swift#L787](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L787)). iOS may purge Caches under storage pressure (inferred from the Apple directory choice; not stated in the SDK).

```
<Caches>/
  INSTALLATION                         installation id (default user id)
  io.sentry/
    <sha1(DSN URL)>/                   "sentryPath", one per DSN
      envelopes/<time>-<counter>-<uuid>.json
      session.current | session.crashed | session.abnormal
      lastInForeground.timestamp
      app.state | previous.app.state
      breadcrumbs.1.state | breadcrumbs.2.state
      previous.breadcrumbs.1.state | previous.breadcrumbs.2.state
      <field>.state | previous.<field>.state   (context, user, dist, environment, tags, extras, fingerprint)
      timezone.offset
      app.hang.event.json
      replay/
        replay.current | replay.last   (JSON)
        <UUID>/ <t>.png ... crashInfo  (frames of one replay)
  SentryCrash/<bundleName>/
    Reports/<app>-report-<id>.json, <app>-report-<id>-attachments/
    Data/CrashState.json
```

Sources: base and DSN hash ([SentryFileManagerHelper.m#L143-L167](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryFileManagerHelper.m#L143-L167), SHA-1 of the DSN URL string in [SentryDsn.swift#L50-L70](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/SentryDsn.swift#L50-L70)); file names ([SentryFileManagerHelper.m#L169-L196](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryFileManagerHelper.m#L169-L196)); envelope file name ([SentryFileManagerHelper.m#L1024-L1033](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryFileManagerHelper.m#L1024-L1033)); scope fields ([SentryScopePersistentStore.swift#L14-L31](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Persistence/SentryScopePersistentStore.swift#L14-L31), [SentryScopePersistentStore.swift#L202-L214](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Persistence/SentryScopePersistentStore.swift#L202-L214)); replay ([SessionReplayFileManager.swift#L12-L14](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayFileManager.swift#L12-L14)); installation ([SentryInstallation.swift#L74](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentryInstallation.swift#L74)); SentryCrash ([SentryCrash.m#L242-L249](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrash.m#L242-L249), [SentryCrashC.c#L142-L165](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrashC.c#L142-L165)).

## 2. Envelope disk cache

- **Every** envelope is written to `envelopes/` before sending (write-through). The write goes through a temp file then moves into place ([SentryHttpTransport.m#L110-L135](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L110-L135), [SentryFileManager.swift#L323-L345](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentryFileManager.swift#L323-L345)). The write runs async on the transport queue; the source accepts losing an envelope if a hard crash hits before it ([SentryHttpTransport.m#L121-L123](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L121-L123)).
- **Order:** file names start with the timestamp, sorted case-insensitively; the oldest is sent first ([SentryFileManager.swift#L63-L72](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentryFileManager.swift#L63-L72), [SentryFileManagerHelper.m#L626-L641](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryFileManagerHelper.m#L626-L641)).
- **maxCacheItems (30) rotation:** after each store, if the folder holds more than `maxCacheItems`, the oldest files are deleted. Each item of a deleted envelope is recorded as a `cache_overflow` client report. If a deleted envelope carried a session `init: true`, that flag is migrated into a newer envelope with the same session ([SentryFileManager.swift#L283-L320](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentryFileManager.swift#L283-L320), [SentryHttpTransport.m#L256-L265](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L256-L265)). The limit counts envelopes, not bytes (read: no size check in `handleEnvelopesLimit`).
- **90-day purge:** at client init, async, every envelope with file creation date older than 90 days is deleted, in all DSN folders ([SentryClient.m#L196](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryClient.m#L196), [SentryFileManager.swift#L74-L80](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentryFileManager.swift#L74-L80), [SentryFileManagerHelper.m#L989-L1021](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryFileManagerHelper.m#L989-L1021)). No client report is recorded for these (read: plain `removeFileAtPath`).
- **Other deletion triggers:** 2xx / 4xx / 5xx response; envelope fully rate-limited at send time; envelope not deserialisable; request could not be built ([SentryHttpTransport.m#L336-L364](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L336-L364), [SentryHttpTransport.m#L436-L455](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L436-L455)).

### Replay crash recovery

- **Every launch**, the replay integration init (installed even with rates 0) moves `replay.current` → `replay.last` and deletes all other replay folders except the one `replay.last` points to ([SentrySessionReplayIntegration.swift#L116-L117](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L116-L117), [SessionReplayFileManager.swift#L136-L190](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayFileManager.swift#L136-L190)).
- At crash time the handler writes `crashInfo` (binary: last sent segment id, last segment end, replay type) into the replay folder ([SentrySessionReplaySyncC.c](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySessionReplaySyncC.c), called from [SentryCrashC.c#L105](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrashC.c#L105)).
- Recovery is triggered only by a **fatal event** passing the global event processor (crash report, watchdog termination, fatal app hang) ([SentrySessionReplayIntegration.swift#L196-L201](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L196-L201)). `resumePreviousSessionReplay` reads `replay.last`, sets `contexts.replay.replay_id` on the fatal event, and on the processing queue encodes and sends the remaining frames, then deletes the folder and `replay.last` ([SessionReplayRecovery.swift#L48-L101](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayRecovery.swift#L48-L101)).
- What is sent ([SessionReplayRecovery.swift#L115-L168](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayRecovery.swift#L115-L168)): if a segment was already sent (`lastSegmentEnd > 0`), type `session`, next segment id, interval `[lastSegmentEnd, +5 s]`; otherwise the persisted type (default `buffer`), segment 0, the last 30 s of frames; a `buffer` replay is re-sampled with the stored `errorSampleRate` and may be dropped.
- `replay.last` stays on disk until the encode finishes, so a kill during the encode can still be recovered on the following launch ([SessionReplayRecovery.swift#L70-L73](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayRecovery.swift#L70-L73)).
- Inferred: if the previous run ended **without** a fatal event (user swipe-kill, background kill, `exit()`), the last partial segment's frames are not sent and are deleted at the next-but-one cleanup.

## 4. Send at next launch, crash timing

1. Client init creates the transport, which immediately starts `sendAllCachedEnvelopes` (oldest first) ([SentryHttpTransport.m#L86](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L86)). This runs before integrations are installed (they install on main later, [SentrySDKInternal.m#L317-L335](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySDKInternal.m#L317-L335)).
2. Crash integration: finalise previous session (crashed), then convert stored crash reports to events and capture them. Each new envelope is stored and joins the queue behind older cached envelopes (inferred from oldest-first order).
3. Startup crash (crash ≤ 2 s after crash-state init): reports are processed synchronously and the SDK blocks in `flush` for up to 5 s (minus replay-recovery wait, min 1 s) ([SentryCrashReportSink.m#L46-L66](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryCrashReportSink.m#L46-L66), [SentryStartupCrashFlush.swift#L11-L40](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentryStartupCrashFlush.swift#L11-L40)).
4. Session tracking closes the cached session (exited/abnormal) unless the crash integration already handled it ([SentryHub.m#L218-L250](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHub.m#L218-L250)).
5. Hang integration sends a stored fatal app hang; watchdog integration sends a watchdog termination event if the heuristic fires ([SentryHangTrackingIntegration.swift#L176-L203](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/AppHangTracking/SentryHangTrackingIntegration.swift#L176-L203), [SentryWatchdogTerminationTracker.swift#L40-L56](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/WatchdogTerminations/SentryWatchdogTerminationTracker.swift#L40-L56)).

**Crash envelope: written at crash time vs converted later.** At crash time only the raw SentryCrash JSON report (+ attachments, replay crash info, optional saved transaction) is written. The Sentry event and envelope are created at the **next launch** after `SentrySDK.start`, with the **current** scope copied onto it ([SentryStoredCrashReportProcessor.m#L87-L110](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryStoredCrashReportProcessor.m#L87-L110)). If the app is never relaunched, nothing is sent (inferred). Event `timestamp` comes from the report (converter; *uncertain*, `SentryCrashReportConverter` not read line by line).

## 5. Retry, backoff, rate limits

**Response handling** ([SentryHttpTransport.m#L390-L456](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L390-L456)):

| Outcome | Envelope | Client report | Next send |
|---|---|---|---|
| No response (offline, DNS, timeout 15 s, connection lost) | **kept** on disk | none | sending stops; resumes on next trigger |
| Response with transport error (e.g. body read failed) | treated as delivered; status code decides | per status | per status |
| 2xx | deleted | none | next after 0.1 s |
| 429 | deleted | none (Relay counts it) | next after 0.1 s; rate limit stored |
| other 4xx / 5xx | **deleted, not retried** | `send_error` per item | next after 0.1 s |
| other (1xx, 3xx) | kept | none | sending stops |

- There is **no timer-based retry and no exponential backoff** (read: no retry scheduling in the transport). Kept envelopes are retried when something calls `sendAllCachedEnvelopes`: a new envelope is captured, connectivity returns (`NWPathMonitor` callback), `flush`, or the next app start ([SentryHttpTransport.m#L94-L102](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L94-L102), [SentryHttpTransport.m#L180-L238](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L180-L238)).
- **Rate limits.** Every response updates limits. If `X-Sentry-Rate-Limits` is present it is parsed (`retry_after:categories:scope`, comma-separated quotas, semicolon-separated categories, empty categories = all, unknown categories ignored, `metric_bucket` namespaces honoured only for `custom`); otherwise on **429** the `Retry-After` header (seconds, or HTTP date) applies to **all** categories, default **60 s** if missing or unparsable. The longer of old and new expiry wins ([DefaultRateLimits.swift#L44-L66](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/DefaultRateLimits.swift#L44-L66), [RateLimitParser.swift#L5-L105](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/RateLimitParser.swift#L5-L105), [RetryAfterHeaderParser.swift#L23-L39](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/RetryAfterHeaderParser.swift#L23-L39)).
- **Enforcement.** `SentryEnvelopeRateLimit` removes items whose category (or `all`) is limited, both when capturing and again before sending a cached envelope; drops are counted `ratelimit_backoff` ([SentryEnvelopeRateLimit.m#L28-L64](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryEnvelopeRateLimit.m#L28-L64), [SentryHttpTransport.m#L243-L253](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L243-L253)). Session replay additionally **stops** the running replay when `replay` or `all` is limited ([SentrySessionReplayIntegration.swift#L558-L566](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L558-L566)).
- **Categories** (header names): `default`, `error`, `session`, `transaction`, `attachment`, `profile`, `profile_chunk_ui`, `replay`, `metric_bucket`, `span`, `feedback`, `log_item`, `log_byte`, `trace_metric`, `trace_metric_byte` ([SentryDataCategory.swift#L11-L52](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/SentryDataCategory.swift#L11-L52)). Item type mapping: `event`→error, `replay_video`→replay, `profile_chunk`→profile_chunk_ui, `log`→log_item, `statsd`→metric_bucket, unknown → `default` ([SentryDataCategory+EnvelopeItemType.swift#L10-L29](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/SentryDataCategory+EnvelopeItemType.swift#L10-L29)).
- Rate limits are in memory only, so a restart forgets them (§3).

## 6. Offline behaviour

- Envelopes accumulate on disk up to `maxCacheItems` (30); older ones are rotated out with `cache_overflow` reports (§2).
- Connectivity is observed with `NWPathMonitor`; on reconnect the transport resends the cache ([SentryReachability.swift#L37-L65](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/SentryReachability.swift#L37-L65), [SentryHttpTransport.m#L94-L102](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L94-L102)).
- Session replay in **session mode pauses capture** while offline and resumes on reconnect; buffer mode keeps buffering ([SentrySessionReplayIntegration.swift#L607-L618](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L607-L618), [SentrySessionReplay.swift#L249-L259](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L249-L259), [SentrySessionReplay.swift#L475-L477](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L475-L477)). Inferred: a long offline period produces a gap in the replay, not a backlog of segments.
- A replay segment is one envelope; 30 envelopes at one per 5 s ≈ 2.5 minutes of segments if nothing else is queued (inferred arithmetic).

## 7. App kill and background

- **No flush on background.** No `didEnterBackground` / `willResignActive` hook calls `flush` in the client or transport (read: no such observer in `SentryHttpTransport.m` / `SentryClient.m`; *uncertain* that nothing else calls it). On `willResignActive` the log and metric buffers are forwarded to the transport, which writes them to disk ([DefaultTelemetryBufferDataForwardingTriggers.swift#L64-L72](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/TelemetryBuffer/DefaultTelemetryBufferDataForwardingTriggers.swift#L64-L72)). In-flight requests use a normal (not background) `URLSession` (ephemeral), so they may be suspended with the app (inferred).
- **Replay** pauses on `didEnterBackground` and closes the current segment ([SentrySessionReplay.swift#L261-L276](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L261-L276)).
- **willTerminate:** session ended synchronously, app state marked terminated, log/metric buffers forwarded ([SessionTracker.swift#L209-L215](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Session/SessionTracker.swift#L209-L215), [SentryAppStateManager.swift#L220-L224](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/AppState/SentryAppStateManager.swift#L220-L224)).
- **Kill in background / swipe-kill:** no signal handler runs for SIGKILL. Next launch: no crash, app was not active → not a watchdog termination; the session is closed exited at `lastInForeground` ([SentryWatchdogTerminationLogic.swift#L108-L112](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/WatchdogTerminations/SentryWatchdogTerminationLogic.swift#L108-L112), [SentryHub.m#L237-L248](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHub.m#L237-L248)).
- **`shutdownTimeInterval`** (2 s) is only the flush budget of `SentrySDK.close()` ([SentryClient.m#L297](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryClient.m#L297), [SentryHub.m#L1127-L1129](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHub.m#L1127-L1129)).

## 8. Client reports

- On by default (`sendClientReports`). Counters per (category, reason) are kept in memory and attached as a `client_report` item to the **next envelope that is stored** ([SentryHttpTransport.m#L142-L178](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L142-L178), [SentryHttpTransport.m#L269-L296](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L269-L296)).
- Discard reasons: `before_send`, `event_processor`, `sample_rate`, `network_error`, `queue_overflow`, `cache_overflow`, `ratelimit_backoff`, `insufficient_data`, `send_error` ([SentryDiscardReason.swift#L10-L30](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/SentryDiscardReason.swift#L10-L30)).
- Spans in a dropped transaction are counted as `span` (count + 1); logs and trace metrics also count bytes (`log_byte`, `trace_metric_byte`) ([SentryHttpTransport.m#L498-L527](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L498-L527)). Since 9.33.0 every batched log/metric is counted, not one per item ([CHANGELOG.md](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/CHANGELOG.md)).
- 429 responses are not counted by the SDK (Relay does) ([SentryHttpTransport.m#L439-L446](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L439-L446)).

## 9. Size limits

- `maxAttachmentSize` 200 MiB per attachment ([Options.swift#L336](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L336)); the doc comment points to Relay's own limits.
- Log/metric batches: ≤ 100 items or 1 MiB buffer ([TelemetryProcessor.swift#L98-L126](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/TelemetryProcessor/TelemetryProcessor.swift#L98-L126)).
- No SDK-side cap on total envelope size or on cache bytes was found (read in `SentryFileManager` and `SentryHttpTransport`; *uncertain* for other paths). Server-side envelope limits are Relay's ([Relay options docs](https://docs.sentry.io/product/relay/options/), linked from the source; not fetched).
- Replay segment size is bounded by bitrate × 5 s (medium ≈ 25 KB video per segment, inferred arithmetic) plus breadcrumb/touch JSON.

## 10. Facts for a replay store reading from Sentry, or an OTel collector in front of Sentry

Facts only.

1. Replay arrives as one `replay_video` envelope item per 5 s segment; its payload is MessagePack with `replay_event` (JSON), `replay_recording` (rrweb JSON) and `replay_video` (H.264 mp4 bytes) ([SentryEnvelopeItem.swift#L168-L205](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/SentryEnvelopeItem.swift#L168-L205)).
2. Requests are gzip-compressed `POST`s with `X-Sentry-Auth` derived from the DSN, sent to the DSN host; the DSN host can be any URL ([SentryURLRequestFactory.swift#L13-L56](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/SentryURLRequestFactory.swift#L13-L56)).
3. The SDK deletes an envelope on any 4xx or 5xx; only a missing response keeps it. A receiver that returns 5xx during an outage loses that data (read: [SentryHttpTransport.m#L436-L451](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L436-L451)).
4. A receiver can throttle per category with `X-Sentry-Rate-Limits` on any response; a `replay` limit stops the device's current replay, not just one segment ([DefaultRateLimits.swift#L44-L57](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/DefaultRateLimits.swift#L44-L57), [SentrySessionReplayIntegration.swift#L558-L566](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L558-L566)).
5. Envelopes are sent one at a time, oldest first, with `sent_at` set just before sending; the request timeout is 15 s ([SentryHttpTransport.m#L322-L351](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L322-L351), [SentryURLRequestFactory.swift#L11](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/SentryURLRequestFactory.swift#L11)).
6. Segments of one replay can arrive late (after offline periods or at next launch) and out of wall-clock order relative to other replays' segments (inferred from disk cache + oldest-first + next-launch recovery).
7. A crashed session's last segment arrives at the **next launch**, only if that launch produces a fatal event; its segment id continues the sequence, or is 0 with type `buffer` if no segment had been sent ([SessionReplayRecovery.swift#L115-L168](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayRecovery.swift#L115-L168)).
8. Replay ids change with each release-health session (new session after ≥ 30 s background); the replay id is set on the scope and copied to events as `contexts.replay.replay_id` ([SentrySessionReplayIntegration.swift#L579-L583](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L579-L583), [SessionReplayRecovery.swift#L76-L78](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayRecovery.swift#L76-L78)).
9. Each replay event lists the trace ids seen during its segment window (up to 100 buffered) ([SentrySessionReplay.swift#L146](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L146), [SentrySessionReplay.swift#L848-L856](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L848-L856)).
10. Crash events are built at next launch with the scope of the **new** process, while watchdog-termination events use the previous run's persisted scope without trace context (§4, [architecture.md](architecture.md) §8).
11. The SDK's own network instrumentation ignores requests to the DSN host + path, so traffic to a collector at the DSN URL is not traced or breadcrumbed ([SentryNetworkTracker.swift#L789-L797](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/SentryNetworkTracker.swift#L789-L797)).
12. The SDK emits Sentry envelopes only; there is no OTLP output in the tree (inferred from the file list, see [architecture.md](architecture.md) §11).
13. Client reports arrive piggy-backed inside other envelopes, not on their own (§8).
