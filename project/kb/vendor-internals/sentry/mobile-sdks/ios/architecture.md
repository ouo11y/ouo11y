# sentry-cocoa architecture (iOS internals)

sentry-cocoa 9.33.0 (tag, 2026-11-04). Research date 2026-11-10. Method: source read at the tag; docs accessed 2026-11-10.

Feature-level yes/no and main defaults are in [sentry-mobile.md](../../../../client-sdk-features/vendors/sentry-mobile.md). This file goes one level down: which class does what, on which queue, and what lands on disk. Options are in [configuration.md](configuration.md). Disk cache, retries and crash recovery are in [reliability.md](reliability.md).

Legend: **read** = seen in source at the tag. **inferred** = follows from code read, not stated in it. **uncertain** = not confirmed. Unmarked statements with a source link are read.

## 1. Two build flavours in one tree

- The tree compiles a v9 SDK and a v10 preview from the same sources, switched by the `SDK_V10` compile flag. Release 9.33.0 is built without it (read: `#if !SDK_V10` guards everywhere, e.g. [Integrations.swift#L47](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Core/Integrations/Integrations.swift#L47)).
- The crash backend differs: v9 uses the in-tree **SentryCrash** fork (`SentryCrashIntegration`); v10 uses upstream **KSCrash** (`SentryKSCrash.Integration`) ([Integrations.swift#L71-L75](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Core/Integrations/Integrations.swift#L71-L75)). This file describes the v9 path unless it says v10.
- `Options` is a Swift class exported to ObjC as `SentryOptions` ([Options.swift#L4](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L4)). `SentryHub` and `SentryClient` are thin Swift wrappers around ObjC `SentryHubInternal` / `SentryClientInternal` ([SentryHub.swift#L5-L13](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/SentryHub.swift#L5-L13), [SentryClient.swift#L5-L12](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/SentryClient.swift#L5-L12)). A separate `SentryObjCCompat` module wraps `Options` as `SentryObjCOptions` for the v10 ObjC surface ([SentryObjCOptions.swift#L9](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryObjCCompat/SentryObjCOptions.swift#L9)).

## 2. SDK start

In order:

1. `SentrySDK.start(options:)` does not start when env var `XCODE_RUNNING_FOR_PREVIEWS=1`; it only stores the options ([SentrySDK.swift#L106-L117](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentrySDK.swift#L106-L117)). `start(configureOptions:)` builds a fresh `Options` and calls the same path ([SentrySDK.swift#L128-L132](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentrySDK.swift#L128-L132)).
2. `SentrySDKInternal startWithOptions:` warns (does not refuse) on a second start without `close()` ([SentrySDKInternal.m#L267-L275](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySDKInternal.m#L267-L275)), configures SDK logging, counts `startInvocations` and records `startTimestamp` ([SentrySDKInternal.m#L303-L304](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySDKInternal.m#L303-L304)).
3. Option "validation" lives in property setters, not in one validator: an invalid DSN sets `dsn` and `parsedDsn` to nil and logs an error ([Options.swift#L23-L33](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L23-L33)); out-of-range `sampleRate` falls back to 1 ([Options.swift#L282-L298](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L282-L298)); out-of-range `tracesSampleRate` falls back to 0 ([Options.swift#L521-L537](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L521-L537)); `appHangTimeoutInterval <= 0` falls back to 2 s ([Options.swift#L668-L677](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L668-L677)).
4. The client is created synchronously on the calling thread. `SentryClientInternal initWithOptions:` creates `SentryFileManager`, the transports and the thread inspector ([SentryClient.m#L64-L104](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryClient.m#L64-L104)), caches the installation ID async and schedules the 90-day envelope purge ([SentryClient.m#L192-L196](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryClient.m#L192-L196)). Creating the HTTP transport immediately calls `sendAllCachedEnvelopes` ([SentryHttpTransport.m#L86](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L86)).
5. Still on the calling thread: move `app.state` → `previous.app.state`, `breadcrumbs.*.state` → `previous.breadcrumbs.*.state`, and every persisted scope field → `previous.<field>.state` ([SentrySDKInternal.m#L306-L310](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySDKInternal.m#L306-L310)). Build the scope through `initialScope` with `maxBreadcrumbs` and `maxFeatureFlags` ([SentrySDKInternal.m#L312-L314](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySDKInternal.m#L312-L314)).
6. The rest runs on the **main queue**, async if the caller is not on main ([SentrySDKInternal.m#L317-L343](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySDKInternal.m#L317-L343)): start `UIDeviceWrapper`, create `SentryHubInternal(client, scope)` and set it as the global hub, start the binary-image cache, install integrations, call `onLastRunStatusDetermined(.didNotCrash)` when the crash reporter is installed and no fatal was detected, then start profiler tasks. A source comment says the SDK may not be fully initialised right after a background-thread start ([SentrySDKInternal.m#L281-L284](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySDKInternal.m#L281-L284)).
7. One global hub, one scope (no per-thread hubs). Inferred from the single `setCurrentHub` call and the static key `io.sentry.currentScope` ([SentryCurrentScopeStorage.swift#L8](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentryCurrentScopeStorage.swift#L8)).

`SentrySDK.close()` runs synchronously on main: stop the continuous profiler, uninstall integrations, force-stop the app-state manager, `hub close` (flush up to `shutdownTimeInterval`, default 2 s), unbind the client, reset the dependency container ([SentrySDKInternal.m#L668-L703](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentrySDKInternal.m#L668-L703), [SentryClient.m#L297](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryClient.m#L297)).

### Scope sync to SentryCrash

- `SentryCrashScopeObserver` is added to the scope. On every change it serialises user, dist, environment, context, trace context, extras, tags, fingerprint, level, attributes and breadcrumbs to JSON C strings ([SentryCrashScopeObserver.m#L25-L135](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryCrashScopeObserver.m#L25-L135)).
- The C side keeps them in a static `SentryCrashScope` struct (`strdup`, freed on replace), so the crash writer reads them without Objective-C ([SentryScopeSyncC.c#L7-L60](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryScopeSyncC.c#L7-L60)). The breadcrumb ring has `maxBreadcrumbs` slots ([SentryCrashIntegration.swift#L62](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrashV9Swift/SentryCrashIntegration.swift#L62)).
- Release, dist and environment are written into SentryCrash user info at install ([SentryCrashIntegration.swift#L186-L213](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrashV9Swift/SentryCrashIntegration.swift#L186-L213)).

## 5. Transport

- **Factory.** `SentryTransportFactory` builds a `SentryHttpTransport` with `cachedEnvelopeSendDelay: 0.1` s, plus a `SentrySpotlightTransport` when `enableSpotlight` is on ([SentryTransportFactory.m#L25-L60](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryTransportFactory.m#L25-L60)). The `URLSession` is `options.urlSession` if set, else a new `ephemeral` session with `urlSessionDelegate` ([SentryTransportFactory.m#L73-L84](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryTransportFactory.m#L73-L84)).
- **Write-through disk.** `sendEnvelope:` strips rate-limited items, attaches pending client reports, then on the transport queue **writes the envelope to disk** and calls `sendAllCachedEnvelopes` ([SentryHttpTransport.m#L110-L135](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L110-L135)). Nothing is sent from memory unless the disk write fails (`notStoredEnvelopes`).
- **One in flight.** `sendAllCachedEnvelopes` returns if `isSending` or the request manager is busy (`operationCount <= 1`). It reads the **oldest** file, re-applies rate limits, stamps `sent_at`, builds the request and sends ([SentryHttpTransport.m#L299-L368](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L299-L368), [SentryQueueableRequestManager.m#L27-L44](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryQueueableRequestManager.m#L27-L44)). After each delete it schedules the next send 0.1 s later ([SentryHttpTransport.m#L370-L388](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHttpTransport.m#L370-L388)).
- **Request.** `POST` to the DSN envelope URL; `Content-Type: application/x-sentry-envelope`; `Content-Encoding: gzip` (zlib level -1 = default); `User-Agent: <sdkName>/<version>`; `X-Sentry-Auth` with `sentry_version=7`, `sentry_client`, `sentry_key`; timeout **15 s**; cache policy `reloadIgnoringLocalCacheData` ([SentryURLRequestFactory.swift#L10-L56](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/SentryURLRequestFactory.swift#L10-L56)).
- **Response handling and rate limits** (`SentryEnvelopeRateLimit`, `DefaultRateLimits`, `RateLimitParser`): [reliability.md](reliability.md) §4-§5.
- **Wire format.** Sentry envelope. Each replay segment is one `replay_video` item whose payload is **MessagePack** with keys `replay_event`, `replay_recording`, `replay_video` (the mp4 bytes) ([SentryEnvelopeItem.swift#L168-L205](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/SentryEnvelopeItem.swift#L168-L205)).
- **Self-exclusion.** The network tracker skips requests whose host equals the DSN host and whose path contains the DSN API path ([SentryNetworkTracker.swift#L789-L797](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Networking/SentryNetworkTracker.swift#L789-L797)).

## 6. Crash handling (v9 SentryCrash fork)

**Install.** `SentryCrashIntegration.startCrashHandler` sets SIGTERM reporting (default off), installs SentryCrash under `cacheDirectoryPath`, sets `fatalDetected` if the last launch crashed, optionally enables the experimental `__cxa_throw` swap, finalises the previous session, then sends all stored reports ([SentryCrashIntegration.swift#L103-L172](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrashV9Swift/SentryCrashIntegration.swift#L103-L172)).

**Monitors.** Default set `ProductionSafeMinimal` = `All` = Mach exception + POSIX signal + C++ exception + NSException + application state ([SentryCrashMonitorType.h#L41-L87](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrashV9Headers/include/SentryCrashMonitorType.h#L41-L87), [SentryCrashC.c#L60](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrashC.c#L60)). With a debugger attached the debugger-unsafe monitors (Mach, signal, C++, NSException) stay off ([SentryCrashMonitor.c#L157](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/Monitors/SentryCrashMonitor.c#L157)). Monitor sources: [Monitors/](https://github.com/getsentry/sentry-cocoa/tree/9.33.0/Sources/SentryCrash/Recording/Monitors).

**Where on disk.** `<cacheDirectoryPath>/SentryCrash/<bundleName>/` ([SentryCrash.m#L242-L249](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrash.m#L242-L249)), with `Reports/` and `Data/CrashState.json` ([SentryCrashC.c#L142-L165](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrashC.c#L142-L165)). Reports are `<app>-report-<016llx id>.json`, attachments go in `<app>-report-<id>-attachments/`, at most **5** reports are kept ([SentryCrashReportStore.c#L45](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrashReportStore.c#L45), [SentryCrashReportStore.c#L76](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrashReportStore.c#L76), [SentryCrashReportStore.c#L303](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrashReportStore.c#L303)). This is **not** under `io.sentry/<dsn-hash>/`.

**Written at crash time** (`onCrash`, [SentryCrashC.c#L93-L136](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrash/Recording/SentryCrashC.c#L93-L136)):
1. mark the crash in `CrashState.json`;
2. write the standard JSON report (threads, registers, binary images, synced scope), or a recrash report if the handler itself crashed;
3. write session-replay crash info (segment id, last segment end, replay type) into the replay folder (§13);
4. then, **not async-signal-safe** by design: screenshot(s) and view hierarchy into the attachments folder if enabled, and finish/save the scope-bound transaction if `enablePersistingTracesWhenCrashing` ([Options.swift#L361](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L361)).

No Sentry envelope is built at crash time. Memory introspection near the stack is opt-in (`enableMemoryIntrospection`, [SentryCrashIntegration.swift#L60](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/SentryCrashV9Swift/SentryCrashIntegration.swift#L60)).

**Next launch: report → event.** `SentryCrashReportSink.filterReports` processes reports async on a queue, or **synchronously followed by a flush** when the crash happened ≤ **2 s** after crash-state init (startup crash; sets `detectedStartUpCrash`) ([SentryCrashReportSink.m#L11](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryCrashReportSink.m#L11), [SentryCrashReportSink.m#L46-L66](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryCrashReportSink.m#L46-L66)). The startup flush budget is 5 s: it first waits for replay recovery, keeping at least 1 s for the flush ([SentryStartupCrashFlush.swift#L11-L40](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentryStartupCrashFlush.swift#L11-L40)). `SentryStoredCrashReportProcessor` converts with `SentryCrashReportConverter`, copies the **current** hub scope, adds crash-time attachments and calls `captureFatalEventWithResult` ([SentryStoredCrashReportProcessor.m#L46-L110](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryStoredCrashReportProcessor.m#L46-L110)). The hub attaches the stored crashed session to that first fatal event ([SentryHub.m#L296-L324](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHub.m#L296-L324)).

## 8. Watchdog termination detection

Decided at the next launch by `SentryWatchdogTerminationLogic.isWatchdogTermination` ([SentryWatchdogTerminationLogic.swift#L43-L125](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/WatchdogTerminations/SentryWatchdogTerminationLogic.swift#L43-L125)). It is **true** only if all hold:
- option on, `previous.app.state` exists, not a simulator build;
- same release name, OS version, system boot timestamp and `identifierForVendor`;
- previous run: no debugger, no `willTerminate`, SDK running, app **active** (foreground), no hang in progress (`isANROngoing`);
- the crash reporter saw no crash; `SentrySDK.start` was called exactly once in this process.

The app state file is `<sentryPath>/app.state`, JSON keys `release_name`, `os_version`, `vendor_id`, `is_debugging`, `system_boot_timestamp`, `is_active`, `was_terminated`, `is_anr_ongoing`, `is_sdk_running` ([SentryAppState.swift#L7-L104](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/AppState/SentryAppState.swift#L7-L104)). It is rewritten on didBecomeActive, willResignActive, willTerminate and SDK stop ([SentryAppStateManager.swift#L94-L224](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/AppState/SentryAppStateManager.swift#L94-L224)) and on hang start/stop ([SentryWatchdogTerminationTrackingIntegration.swift#L131-L157](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/WatchdogTerminations/SentryWatchdogTerminationTrackingIntegration.swift#L131-L157)). There is no periodic heartbeat (inferred: no timer writes it).

The event is `level: fatal`, exception type `WatchdogTermination`, mechanism `watchdog_termination`, value "The OS watchdog terminated your app, possibly because it overused RAM." It is built from the **previous** run's persisted user, dist, environment, tags, extras, fingerprint, context and breadcrumbs; its timestamp is the last breadcrumb's ([SentryWatchdogTerminationTracker.swift#L58-L117](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/WatchdogTerminations/SentryWatchdogTerminationTracker.swift#L58-L117), [SentryWatchdogTerminationConstants.swift](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/WatchdogTerminations/SentryWatchdogTerminationConstants.swift)). It goes through `captureFatalEvent`, so it counts as fatal and triggers replay recovery (§13). Trace context is deliberately not persisted ([SentryWatchdogTerminationTrackingIntegration.swift#L109-L111](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/WatchdogTerminations/SentryWatchdogTerminationTrackingIntegration.swift#L109-L111)).

Hang signal: the ANR tracker (default) or, with `experimental.enableWatchdogTerminationsV2`, the run-loop based `SentryDefaultAppHangTracker` (~25 ms polling) ([SentryWatchdogTerminationTrackingIntegration.swift#L57-L63](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/WatchdogTerminations/SentryWatchdogTerminationTrackingIntegration.swift#L57-L63), [SentryAppHangTracker.swift#L17-L23](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/AppHangTracking/SentryAppHangTracker.swift#L17-L23)).

## 9. App hang tracking (deprecated for v10)

- **Tracker choice.** iOS, tvOS and visionOS with UIKit always use **V2** (frames-based). V1 (main-queue ping) is used elsewhere, e.g. macOS ([SentryDependencyContainer.swift#L585-L598](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/SentryDependencyContainer.swift#L585-L598)). No option selects it.
- **V2 detection** ([SentryANRTrackerV2.swift#L56-L171](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/AppHangTracking/SentryANRTrackerV2.swift#L56-L171)): a thread sleeps `timeout / 5` (400 ms at the 2 s default) and asks the frames tracker for the frame delay over the last `timeout`. **Fully blocking**: one frame contributes and delay ≥ timeout. **Non-fully blocking**: several frames contribute and delay > 0.99 × timeout. **Stop**: delay over the last `2 × timeout / 5` is below 20 % of that window. No new hang within `timeout` after a stop.
- `enableReportNonFullyBlockingAppHangs` (default true) only filters `.nonFullyBlocking` at report time ([SentryHangTrackingIntegration.swift#L88-L90](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/AppHangTracking/SentryHangTrackingIntegration.swift#L88-L90)). Hangs are reported only while the app state is `.active` ([SentryHangTrackingIntegration.swift#L92](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/AppHangTracking/SentryHangTrackingIntegration.swift#L92)).
- **V2 lifecycle (iOS).** On detection the SDK builds the event (main-thread stack, all threads, debug meta, scope applied, `app.in_foreground = true`) and **stores it to disk** as `app.hang.event.json` instead of sending ([SentryHangTrackingIntegration.swift#L100-L126](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/AppHangTracking/SentryHangTrackingIntegration.swift#L100-L126)). On stop it reads and deletes the file, sets the message to "App hanging between X and Y seconds." and sends a **non-fatal** error ([SentryHangTrackingIntegration.swift#L142-L163](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/AppHangTracking/SentryHangTrackingIntegration.swift#L142-L163)).
- **Fatal app hang.** If the process dies during the hang, the file survives. At the next launch the integration sends it with `level: fatal`, `handled: false`, a fatal exception type and the value "The user or the OS watchdog terminated your app while it blocked the main thread for …", through `captureFatalAppHang`. If the previous run crashed instead, the stored hang is sent as a normal event ([SentryHangTrackingIntegration.swift#L176-L203](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/AppHangTracking/SentryHangTrackingIntegration.swift#L176-L203)). The hub ends the stored session as **abnormal** with mechanism `anr_foreground` and attaches it ([SentryHub.m#L345-L366](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHub.m#L345-L366), [PreviousRunSessionFinalizer.swift#L77-L93](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Session/PreviousRunSessionFinalizer.swift#L77-L93)).
- Deprecation: `enableAppHangTracking`, `enableReportNonFullyBlockingAppHangs` and `pause/resumeAppHangTracking` point to MetricKit ([Options.swift#L633-L657](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Options.swift#L633-L657), [SentrySDK.swift#L841-L851](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentrySDK.swift#L841-L851)).

## 10. Session tracking (release health)

`SessionTracker` ([SessionTracker.swift](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Session/SessionTracker.swift)):
- **start()** first closes any cached session from the previous run, then observes `didBecomeActive` (and the hybrid `SentryHybridSdkDidBecomeActive`), `willResignActive` and `willTerminate`; it starts a session immediately if the app is already active ([SessionTracker.swift#L45-L75](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Session/SessionTracker.swift#L45-L75)). Background launches do not start sessions.
- **Background 30 s.** `willResignActive` stores `lastInForeground.timestamp`. On the next `didBecomeActive`, if background time ≥ `sessionTrackingIntervalMillis` (30 000 ms), the old session ends **at the time the app left the foreground** and a new one starts; otherwise the session continues ([SessionTracker.swift#L138-L207](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Session/SessionTracker.swift#L138-L207)). There is no timer: the decision is taken lazily on return to the foreground.
- **willTerminate** ends the session synchronously as exited, at the last-foreground time ([SessionTracker.swift#L209-L215](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Session/SessionTracker.swift#L209-L215)).
- **Previous run.** `PreviousRunSessionFinalizer` ends the stored session as **crashed** (crash or watchdog termination; end = now − active duration since crash) into `session.crashed`, or **abnormal** (fatal app hang) into `session.abnormal` ([PreviousRunSessionFinalizer.swift#L55-L94](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Session/PreviousRunSessionFinalizer.swift#L55-L94)). Otherwise `closeCachedSession` ends it **exited** at `lastInForeground`, or **abnormal** at its own start time when no timestamp exists ([SentryHub.m#L218-L250](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHub.m#L218-L250)).
- **Files.** `<sentryPath>/session.current`, `session.crashed`, `session.abnormal`, `lastInForeground.timestamp` ([SentryFileManagerHelper.m#L169-L178](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryFileManagerHelper.m#L169-L178)). `session.current` is rewritten on start and on every error-count increment ([SentryHub.m#L144](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHub.m#L144), [SentryHub.m#L264-L270](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Sentry/SentryHub.m#L264-L270)).
- A session starts a replay (§13): a new session after 30 s in background means a new replay id (`sentrySessionStarted` → `startSession`, [SentrySessionReplayIntegration.swift#L239-L247](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L239-L247)).

The app-start profiling decision is taken on the previous launch ([SentryProfileOptions.swift#L66-L77](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Core/Integrations/Performance/SentryProfileOptions.swift#L66-L77)).

**Logs and metrics.** `SentrySDK.logger` ([SentrySDK.swift#L51](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentrySDK.swift#L51)) and `SentrySDK.metrics` ([SentrySDK.swift#L95](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Helper/SentrySDK.swift#L95)). Each has an **in-memory** buffer that flushes after 5 s, at 100 items or at 1 MiB, and on `willResignActive` / `willTerminate` ([TelemetryProcessor.swift#L96-L134](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/TelemetryProcessor/TelemetryProcessor.swift#L96-L134), [DefaultTelemetryBufferDataForwardingTriggers.swift#L31-L72](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Tools/TelemetryBuffer/DefaultTelemetryBufferDataForwardingTriggers.swift#L31-L72)). Inferred: buffered logs are lost on a crash.

**User feedback.** Form via `SentrySDK.feedback.show()`, SwiftUI `sentryFeedback(isPresented:)`, or the deprecated widget. Shake detection swizzles `UIWindow.motionEnded(_:with:)` ([SentryShakeDetector.swift#L15-L55](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/UserFeedback/SentryShakeDetector.swift#L15-L55)); the screenshot trigger observes `userDidTakeScreenshotNotification` ([SentryUserFeedbackIntegrationDriver.swift#L241](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/UserFeedback/SentryUserFeedbackIntegrationDriver.swift#L241)). Opening the form captures a replay (flush in session mode, or send the 30 s buffer) ([SentryUserFeedbackFormController.swift#L278](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/UserFeedback/SentryUserFeedbackFormController.swift#L278), [SentrySessionReplay.swift#L406-L416](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L406-L416)).

**Attachments.** Screenshot and view hierarchy come from attachment processors on the client, for events with an exception or error, **not** for fatal, MetricKit or app-hang events. They are captured on the main thread; `beforeCaptureScreenshot` / `beforeCaptureViewHierarchy` can veto; files `screenshot.png`, `screenshot-2.png`, … one per window ([SentryScreenshotIntegration.swift#L77-L108](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Screenshot/SentryScreenshotIntegration.swift#L77-L108), [SentryViewHierarchyIntegration.swift#L85-L111](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/ViewHierarchy/SentryViewHierarchyIntegration.swift#L85-L111)). For crashes they are taken inside the crash handler via `sentrycrash_setSaveScreenshots` ([SentryScreenshotIntegration.swift#L46-L57](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Screenshot/SentryScreenshotIntegration.swift#L46-L57)). Screenshots use `options.screenshot` masking (text and images masked by default) ([SentryScreenshotOptions.swift#L11-L22](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/Screenshot/SentryScreenshotOptions.swift#L11-L22)).

## 13. Session Replay pipeline (internals only)

1. **Start.** On each Sentry session start: `random < sessionSampleRate` → session mode; else `onErrorSampleRate > 0` → buffer mode; else no replay. If no window exists yet, it waits for `didBecomeActive` / scene activation ([SentrySessionReplayIntegration.swift#L249-L291](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L249-L291)). It creates `<sentryPath>/replay/<UUID>/`, writes `replay/replay.current` (JSON `replayId`, `path`, `errorSampleRate`, `replayType`) and points the crash-safe C info at `<UUID>/crashInfo` ([SessionReplayFileManager.swift#L34-L63](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayFileManager.swift#L34-L63), [SessionReplayFileManager.swift#L108-L134](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SessionReplayFileManager.swift#L108-L134)).
2. **Scheduler.** `CFRunLoopObserver` on the main run loop, `.commonModes`, order `CFIndex.max`; fires at `beforeWaiting` / `exit` after a busy pass and reports whether the mode is `.tracking` ([SentrySessionReplayRunLoopCaptureScheduler.swift#L57-L103](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayRunLoopCaptureScheduler.swift#L57-L103)).
3. **Gate.** `captureFrameIfNeeded`: stop at `maximumDuration` (1 h); one capture in flight; at most `frameRate` (1 fps); activity guard (scrolling, tracking controls and gestures = interaction; ≥ 4 animation keys = animation) ([SentrySessionReplay.swift#L469-L554](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L469-L554), [SentrySessionReplayCaptureGuard.swift#L15-L44](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayCaptureGuard.swift#L15-L44)). Animations defer in 0.25 s steps up to 1 s; a main-thread cost ≥ 150 ms doubles the interval up to 2 s ([SentrySessionReplay.swift#L649-L667](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L649-L667)).
4. **Redact + render (main thread).** `redactRegionsFor(view:)` walks layers ([SentryUIRedactBuilder.swift#L448](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Core/Tools/ViewCapture/SentryUIRedactBuilder.swift#L448)); `SentryViewRendererV2` draws at `screen.scale` with `drawHierarchy(afterScreenUpdates: false)`, or `layer.render(in:)` with fast rendering ([SentryViewRendererV2.swift#L18-L24](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Core/Tools/ViewCapture/SentryViewRendererV2.swift#L18-L24), [SentryViewPhotographer.swift#L66-L96](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Core/Tools/ViewCapture/SentryViewPhotographer.swift#L66-L96)).
5. **Mask (background).** Redraw at 1x with `interpolationQuality = .none` and fill the regions ([SentryViewPhotographer.swift#L80-L86](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Core/Tools/ViewCapture/SentryViewPhotographer.swift#L80-L86), [SentryDefaultMaskRenderer.swift#L27](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Core/Tools/ViewCapture/SentryDefaultMaskRenderer.swift#L27)).
6. **Frames on disk.** Each masked frame is PNG-encoded, written as `<UUID>/<timeIntervalSinceReferenceDate>.png` and kept in memory; the oldest are trimmed beyond `cacheMaxSize` ([SentryOnDemandReplay.swift#L113-L146](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentryOnDemandReplay.swift#L113-L146)). `cacheMaxSize = duration × frameRate + 1`: 6 frames in session mode, 31 in buffer mode ([SentrySessionReplayIntegration.swift#L378-L388](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L378-L388)).
7. **Encode.** Per 5 s segment ([SentrySessionReplay.swift#L717-L726](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L717-L726)): `AVAssetWriter` `.mp4`, H.264 Main AutoLevel, no frame reordering, max keyframe interval 6, average bitrate from quality ([SentryOnDemandReplay.swift#L334](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentryOnDemandReplay.swift#L334), [SentryOnDemandReplay.swift#L381-L414](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentryOnDemandReplay.swift#L381-L414)). Bitrate = `quality.rawValue × 20 000 + 20 000` (low 20 kbps, medium 40, high 60); `sizeScale` 0.8 for low, else 1.0 ([SentryReplayOptions.swift#L106-L112](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentryReplayOptions.swift#L106-L112)).
8. **Segment event.** `captureSegment` builds a `SentryReplayEvent` (replay id, segment id, start, end, screen names as `urls`, trace ids seen in the window) and an rrweb recording (video event, breadcrumbs, touches from the `sendEvent` swizzle, an options event on segment 0), hands both to the hub, then deletes the mp4 ([SentrySessionReplay.swift#L839-L887](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L839-L887), [SentryTouchTracker.swift#L84](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentryTouchTracker.swift#L84)). After the hub accepts it, the C crash info is updated with the segment id and end time ([SentrySessionReplayIntegration.swift#L555-L577](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L555-L577)).
9. **Buffer mode.** On an event with an error or exception, if `random <= onErrorSampleRate`, it encodes the last `errorReplayDuration` (30 s) as type `buffer` and switches to session mode ([SentrySessionReplay.swift#L365-L438](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L365-L438), [SentrySessionReplayIntegration.swift#L553](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L553)).
10. **Lifecycle.** `didEnterBackground` pauses and closes the current segment; `didBecomeActive` resumes ([SentrySessionReplayIntegration.swift#L392-L405](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L392-L405), [SentrySessionReplayIntegration.swift#L620-L628](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L620-L628), [SentrySessionReplay.swift#L261-L276](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L261-L276)). **Offline** pauses session-mode capture until connectivity returns ([SentrySessionReplayIntegration.swift#L607-L618](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L607-L618), [SentrySessionReplay.swift#L249-L259](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplay.swift#L249-L259)). An active `replay` or `all` rate limit **stops** the replay ([SentrySessionReplayIntegration.swift#L558-L566](https://github.com/getsentry/sentry-cocoa/blob/9.33.0/Sources/Swift/Integrations/SessionReplay/SentrySessionReplayIntegration.swift#L558-L566)).
11. **Crash recovery:** [reliability.md](reliability.md) §3.
