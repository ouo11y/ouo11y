## 2. Envelope cache rules

- **Every envelope goes to disk first**, then is sent. `EnvelopeSender.flush` calls `storeEnvelope` before the HTTP call, and `discard` (delete) after success ([AsyncHttpTransport.java#L270-L300](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/AsyncHttpTransport.java#L270-L300)). Envelopes re-sent from the cache use the `Cached` hint and are not stored twice ([#L83-L87](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/AsyncHttpTransport.java#L83-L87)).
- File name: random `SentryUUID` + `.envelope`, remembered per envelope object ([EnvelopeCache.java#L429-L441](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/cache/EnvelopeCache.java#L429-L441)).
- **Rotation**: before each write, if `*.envelope` count ≥ `maxCacheItems` (30), the oldest files (by `lastModified`) are deleted until there is room. A deleted envelope is counted as `cache_overflow`. If the deleted file held a session "init" flag, the flag is moved to the next file ([CacheStrategy.java#L90-L115](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/cache/CacheStrategy.java#L90-L115), [#L118-L128](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/cache/CacheStrategy.java#L118-L128), [SentryOptions.java#L206](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/SentryOptions.java#L206)).
- The limit is a **file count, not bytes**. One replay segment, one error with a 20 MiB attachment, or one batch of 100 logs each count as one file (inferred from `rotateCacheIfNeeded(allEnvelopeFiles())`).
- Session envelopes: `SessionStart` moves `session.json` → `previous_session.json` and writes the new one; `SessionEnd` deletes `session.json` ([EnvelopeCache.java#L123-L149](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/cache/EnvelopeCache.java#L123-L149)).

## 3. Retry and backoff

There is **no timed retry or exponential backoff**. A failed send either deletes the file or leaves it for the next trigger.

Hints involved:
- `Retryable` (`setRetry`) tells the cache sender whether to keep the file ([EnvelopeSender.java#L91-L106](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/EnvelopeSender.java#L91-L106)).
- `DiskFlushNotification` unblocks a crashing thread once the envelope is on disk ([AsyncHttpTransport.java#L276-L289](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/AsyncHttpTransport.java#L276-L289)).
- `SendCachedEnvelopeHint` = `Cached + Retryable + SubmissionResult + Flushable + Enqueable` ([DirectoryProcessor.java#L112-L113](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/DirectoryProcessor.java#L112-L113)).

Retry triggers for kept files (`SendCachedEnvelopeIntegration`):
1. SDK init (every launch) ([SendCachedEnvelopeIntegration.java#L50-L64](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/SendCachedEnvelopeIntegration.java#L50-L64)).
2. Connectivity change to any state other than `DISCONNECTED` ([#L76-L82](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/SendCachedEnvelopeIntegration.java#L76-L82)).

Not a trigger: the end of a rate limit (inferred: the integration only observes connection status; it registers no rate-limit observer).

Each run skips when offline or when the `All` category is rate-limited ([#L109-L129](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/SendCachedEnvelopeIntegration.java#L109-L129)). Files are processed one by one with a 100 ms pause to avoid bursts; already-submitted paths are skipped ([DirectoryProcessor.java#L21](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/DirectoryProcessor.java#L21), [#L58-L95](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/DirectoryProcessor.java#L58-L95)). A file that fails to deserialize is deleted ([EnvelopeSender.java#L57-L106](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/EnvelopeSender.java#L57-L106)).

Startup crash: if `outbox/startup_crash` exists, `Sentry.init` blocks up to `startupCrashFlushTimeoutMillis` (5000) for the first cache send, once per launch ([SendCachedEnvelopeIntegration.java#L149-L163](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/SendCachedEnvelopeIntegration.java#L149-L163)). The marker is deleted when read ([AndroidEnvelopeCache.java#L128-L155](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/cache/AndroidEnvelopeCache.java#L128-L155)).

Crash-time race (inferred): the transport has one worker thread. If it is busy with a slow upload (30 s timeouts), the crash envelope may not reach disk within the 4 s `flushTimeoutMillis` the crashing thread waits ([UncaughtExceptionHandlerIntegration.java#L136-L144](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/UncaughtExceptionHandlerIntegration.java#L136-L144)). The same applies if 30 envelopes are already queued: the crash envelope is dropped as `queue_overflow`.

## 4. Rate limits

- Parsed from `X-Sentry-Rate-Limits` (`seconds:cat1;cat2:scope:reason[:namespaces]`, comma-separated). Empty category list = all categories. Unknown categories are ignored. Without that header, a 429 applies `Retry-After` (default **60 s** when absent or invalid) to all categories ([RateLimiter.java#L42](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/RateLimiter.java#L42), [#L255-L311](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/RateLimiter.java#L255-L311), [HttpConnection.java#L226-L238](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/HttpConnection.java#L226-L238)). The header is read on every response, not only 429.
- A longer deadline replaces a shorter one, never the reverse ([RateLimiter.java#L319-L327](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/RateLimiter.java#L319-L327)).
- Item type → category: `event`→error, `session`→session, `attachment`→attachment, `profile`→profile, `profile_chunk`→profile_chunk_ui + profile_chunk, `transaction`→transaction, `check_in`→monitor, `replay_video`→replay, `feedback`→feedback, `log`→log_item + log_byte, `span`→span, `trace_metric`→trace_metric + trace_metric_byte, else unknown ([RateLimiter.java#L213-L244](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/RateLimiter.java#L213-L244)).
- Before sending, limited items are removed and counted as `ratelimit_backoff`; if nothing is left the envelope is dropped (and a cached file deleted) ([RateLimiter.java#L95-L135](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/RateLimiter.java#L95-L135), [AsyncHttpTransport.java#L89-L94](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/AsyncHttpTransport.java#L89-L94)).
- Rate limits live **in memory only** (a map of deadlines). A restart forgets them (inferred: no file I/O in `RateLimiter`) ([RateLimiter.java#L46](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/RateLimiter.java#L46)).
- Observers are notified when a limit starts and again when it expires (timer executor) ([RateLimiter.java#L327-L345](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/RateLimiter.java#L327-L345)). Replay is one observer: it **pauses recording** while `All` or `Replay` is limited, and a buffered on-error capture is skipped with one `ratelimit_backoff` replay report ([ReplayIntegration.kt#L592-L604](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-replay/src/main/java/io/sentry/android/replay/ReplayIntegration.kt#L592-L604), [BufferCaptureStrategy.kt#L105-L115](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-replay/src/main/java/io/sentry/android/replay/capture/BufferCaptureStrategy.kt#L105-L115)).
- `isHealthy()` is false while any limit is active or the queue rejected in the last 2 s ([AsyncHttpTransport.java#L160-L164](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/AsyncHttpTransport.java#L160-L164), [QueuedThreadPoolExecutor.java#L34](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/QueuedThreadPoolExecutor.java#L34)).

- `ReplayIntegration.finalizePreviousReplay` reads `replay.json` and `breadcrumbs.json` (next section).

### 5.1 Crashed replay, next launch

From [ReplayIntegration.kt#L663-L725](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-replay/src/main/java/io/sentry/android/replay/ReplayIntegration.kt#L663-L725):

1. On the executor, read the previous replay id from `.scope-cache/replay.json`. None, empty, or one from this process → only clean up.
2. `ReplayCache.fromDisk` reads `replay_<id>/.ongoing_segment`; if it is missing or invalid, the folder is deleted ([ReplayCache.kt#L371-L381](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-replay/src/main/java/io/sentry/android/replay/ReplayCache.kt#L371-L381)).
3. Encode the leftover JPEG frames into one last segment (same segment id, recorder config, replay type `session`/`buffer`), add persisted breadcrumbs and rrweb events, and capture it with a `PreviousReplayHint` (`Backfillable`).
4. Because the hint is backfillable, the envelope builder deletes the whole `replay_<id>` folder after serialising ([SentryClient.java#L349-L351](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/SentryClient.java#L349-L351), [SentryEnvelopeItem.java#L606-L612](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/SentryEnvelopeItem.java#L606-L612)). For normal segments only the mp4 is deleted.
5. All other `replay_*` folders not from this process (and not the one being finalized) are deleted ([ReplayIntegration.kt#L649-L660](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-replay/src/main/java/io/sentry/android/replay/ReplayIntegration.kt#L649-L660)).

In buffer mode, a crash does not encode at crash time; the buffer is turned into the final segment on next launch ([BufferCaptureStrategy.kt#L94-L103](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-replay/src/main/java/io/sentry/android/replay/capture/BufferCaptureStrategy.kt#L94-L103)). Inferred: whether that buffered replay is sent depends on the persisted replay id and `onErrorSampleRate` handling in `ApplicationExitInfoEventProcessor`/`CaptureStrategy`; exact rule **uncertain**.

### 5.2 Previous session finalisation

`PreviousSessionFinalizer` runs on the executor after init. It waits up to `sessionFlushTimeoutMillis` (15 s) for the new session flush, reads `previous_session.json`, marks it `crashed` if a native crash marker exists (timestamp from the marker), else ends it now unless an abnormal exit already ended it, captures it, deletes the marker and the file ([PreviousSessionFinalizer.java#L22-L28](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/PreviousSessionFinalizer.java#L22-L28), [#L53](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/PreviousSessionFinalizer.java#L53), [#L83-L136](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/PreviousSessionFinalizer.java#L83-L136)). ANR v2 and tombstone hints close it as `abnormal`/`crashed` with the OS exit timestamp ([EnvelopeCache.java#L219-L270](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/cache/EnvelopeCache.java#L219-L270)).

## 6. Offline behaviour

- Connectivity comes from `AndroidConnectionStatusProvider` ([AndroidOptionsInitializer.java#L177-L181](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/AndroidOptionsInitializer.java#L177-L181)). Only `DISCONNECTED` blocks sending; `UNKNOWN` and `NO_PERMISSION` send ([AndroidTransportGate.java#L23-L33](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/AndroidTransportGate.java#L23-L33)).
- Offline envelopes are written and kept (§3). With 30 files max, a long offline period keeps only the newest ~30 envelopes (inferred from rotation).
- On reconnect, cached files are sent (§3 trigger 2).
- Replay pauses while offline and resumes on reconnect ([ReplayIntegration.kt#L575-L589](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-replay/src/main/java/io/sentry/android/replay/ReplayIntegration.kt#L575-L589)). So offline time is a gap in the replay, not buffered video.

## 7. App background and kill

- Background: replay pauses at once (in session mode `pause()` captures the current partial segment), log and metric batches flush, the session ends after 30 s ([LifecycleWatcher.java#L94-L130](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/LifecycleWatcher.java#L94-L130), [SessionCaptureStrategy.kt#L65-L70](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-replay/src/main/java/io/sentry/android/replay/capture/SessionCaptureStrategy.kt#L65-L70), [AndroidLoggerBatchProcessor.java#L26-L43](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/AndroidLoggerBatchProcessor.java#L26-L43)).
- No transport flush on background was found (grep of `onBackground` listeners: system events, logs, metrics, lifecycle watcher, ANR profiling, connection status). Envelopes already queued keep sending while the process lives (inferred).
- Kill by the user/OS (no crash): nothing runs. The session is closed on next launch by the finalizer; on API 30+ the exit can surface via ApplicationExitInfo (ANR, tombstone, MemoryLimiter) (§5.2).
- `Sentry.close()`: waits up to `flushTimeoutMillis` (4 s) for the transport, then `shutdownNow` and writes the in-flight envelope to disk ([AsyncHttpTransport.java#L172-L200](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/AsyncHttpTransport.java#L172-L200)).

## 8. Backpressure

`BackpressureMonitor` (check every 10 s, halves `tracesSampleRate` per unhealthy check up to factor 2^10) only starts on the JVM, not on Android ([BackpressureMonitor.java#L15-L17](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/backpressure/BackpressureMonitor.java#L15-L17), [Sentry.java#L719-L725](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/Sentry.java#L719-L725), [TracesSampler.java#L84-L88](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/TracesSampler.java#L84-L88)). On Android the only backpressure is the fixed queues: transport 30, executor 271, logs 1000, metrics 10 000.

## 12. Facts for a replay store reading from Sentry / an OTel collector in front of Sentry

Facts only.

1. The SDK POSTs gzip-compressed envelopes (`Content-Type: application/x-sentry-envelope`, `Content-Encoding: gzip`) to the DSN host ([HttpConnection.java#L129-L130](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/HttpConnection.java#L129-L130)).
2. Only HTTP **200** is treated as success. Any other 2xx is treated as a failure: the file is kept on a live send and deleted on a re-send from cache (inferred from [AsyncHttpTransport.java#L304-L323](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/transport/AsyncHttpTransport.java#L304-L323)).
3. Any 4xx/5xx response, including 503, makes the SDK **delete** the envelope; there is no server-error retry. Only connection-level failures (IOException) and offline keep the file.
4. A 429 or an `X-Sentry-Rate-Limits` header on any response sets in-memory per-category deadlines (default 60 s); limited items are dropped client-side, not queued.
5. Replay arrives as one envelope item of type `replay_video` per 5 s segment, payload msgpack with `replay_event`, `replay_recording` (rrweb JSON) and `replay_video` (H.264 MP4, 1 fps, keyframe every 6 s) ([SentryEnvelopeItem.java#L559-L600](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/SentryEnvelopeItem.java#L559-L600)).
6. A `replay_video` rate limit (category `replay`) or `All` also **pauses recording** on the device, creating gaps.
7. Replay also pauses while offline; segments from that time do not exist.
8. Segments may arrive late and out of order: retries happen only on next launch or reconnect, with 100 ms spacing, and the last segment of a crashed session is built and sent on the next launch.
9. At most 30 envelopes are kept on disk; older ones are rotated out (`cache_overflow`). Long offline periods lose older segments/errors.
10. Client reports (`client_report` items) ride on other envelopes; a proxy that strips or rejects envelopes changes what the SDK counts only if it returns ≥ 400 (`send_error`).
11. The SDK identifies itself as `sentry.java.android/8.63.0` in the SDK info (from `SentryAndroidOptions` constructor, [SentryAndroidOptions.java#L332-L346](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry-android-core/src/main/java/io/sentry/android/core/SentryAndroidOptions.java#L332-L346)); RN apps report the RN SDK name via hybrid configuration (**uncertain**: not traced).
12. Only one DSN is supported per init; the on-disk cache is partitioned by DSN hash, so changing the DSN orphans old cached files (inferred from [SentryOptions.java#L1118-L1124](https://github.com/getsentry/sentry-java/blob/8.63.0/sentry/src/main/java/io/sentry/SentryOptions.java#L1118-L1124)).
