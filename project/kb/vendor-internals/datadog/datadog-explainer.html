Datadog RUM internals

What the Datadog SDKs send, how they batch and retry, and what a replay segment looks like. The data comes from a local capture of the browser SDK 7.17.0 and dd-sdk-ios 3.21.0, plus source at pinned tags. Step 6 vendor research, 2026-11-10.

1. From SDK to intake

Browser and mobile follow the same model: collect events, assemble them, batch them, compress them, POST them. They differ in where the batch lives (memory or disk) and in how they authenticate (URL parameters or headers).

2. What a replay request looks like

Every platform uses a multipart request with a deflated segment part and an event metadata part. Inside the segment, the browser and mobile record formats differ.

5. Findings

  1. The browser replay is no longer rrweb. v7 sends a compact "Change" encoding by default: a string table with roles, implicit node ids and relative insertion points. The docs still say rrweb.
  2. Mobile replay is pure wireframes. Typed rectangles (shape, text, image, placeholder, webview) are masked on the device. The observed iOS cost was about 34 KB/min on a simple screen; the docs average is about 12 KB/s on iOS and 1.2 KB/s on Android.
  3. The browser keeps nothing across page loads. The retry queue is in memory and the exit flush is a beacon, without fetch keepalive. Mobile writes batches to disk first, and they survived an app kill in our test.
  4. Sampling is deterministic and the same everywhere (Knuth factor on the session id). Replay and trace rates are children of the session rate.
  5. Replay segments can now be read through a public API, but the response format is undocumented. A bridge must reverse-engineer and version it.
