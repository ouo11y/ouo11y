1. Five things to know

  • Two ingestion streams. Analytics events go to /e/ or /i/v0/e/. Replay goes to /s/, which is a separate capture deployment and a separate Kafka topic. Errors are ordinary $exception events that capture splits off by name. observed
  • Web replay is rrweb with partial compression. FullSnapshot and Mutation payloads are gzipped per event (cv: "2024-10"). Clicks, console and network stay plain JSON, so the server can count activity without decompressing. observed
  • Mobile replay is rrweb events carrying a "wireframe" node tree (or one screenshot node). The server stores it as sent, and the player turns it into HTML at playback. read
  • Web delivery is in memory. There is a 3 s batch timer, retries with exponential backoff (10 tries), and one sendBeacon at pagehide. Native mobile uses one file per event and retries without limit. observed read
  • Replay storage is blocks in S3 indexed by ClickHouse. Snappy-compressed NDJSON blocks are appended into shared objects and addressed by byte range. session_replay_events holds the block URLs and the counters. Deletion is crypto-shredding. read

4. Replay storage and read-back

Retention picks the prefix (30d, 90d, 1y, 5y). The cloud default is 30 d, and self-hosted defaults to 5 y. ClickHouse has no TTL. Deleting a recording deletes its key (crypto-shredding) and sets is_deleted.
