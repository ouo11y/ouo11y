# Single-file compose quickstart (N29)

Question: how do we let someone run the whole ouo stack by copying **one** compose file,
without cloning the repo, and keep that file from drifting from `deploy/compose/`?

## The quickstart is the stack as released

The first version inlined the configs from the working tree. That broke the day roadmap 8b
(#49) merged: `deploy/compose/rum-api/config.yaml` on `main` gained `admin_token`, `retention`
and `projects`, and the released `rum-api:0.3.0` refuses unknown keys
(`field admin_token not found in type config.Auth`, exit 2). The same break hits
`compose.yaml + compose.images.yaml` on `main` until the next rum-api release: **configs on
`main` may need images that are not released yet.**

So configs come from release commits, never from `main`. CI needs the tags: the `quickstart`
job checks out with `fetch-depth: 0`.

## Images released from different commits: `:latest` + per-image configs (2026-10-27)

The first design required `collector-v<pin>`, `rum-api-v<pin>`, `grafana-v<pin>` on ONE commit.
Components release separately (collector 0.4.0 on `45ac795`, rum-api 0.5.0 on `2654db3`,
grafana 0.5.0 / plugin 0.9.0 on `42a2e07`), so the script refused and the quickstart sat on
0.3.0 for three releases; the founder noticed because the session Timeline still showed (plugin
0.9.0 hides it). Now:

- The ouo images default to `:latest`; the header records the version and index digest the
  file was generated for, the newest `<image>-vX.Y.Z` tag of each (rcs ignored). Pin with
  `OUO_GRAFANA_VERSION=0.5.0` or `0.5.0@sha256:...` (Compose accepts tag@digest; verified).
- `release-images.yml` moves `:latest` only when the tag is the newest final version of the image
  (before, any final tag moved it, so a patch to an older line would have pulled `:latest` back).
- Each image's configs come from the commit its own tag points at (collector/ from
  `collector-v*`, rum-api/ from `rum-api-v*`, grafana/ from `grafana-v*`), Loki / Tempo / Mimir
  from the newest of the three; the service-block check compares each service with
  `compose.yaml` at the same commit, images compared up to the `:-<version>` default.
- `--check` also fails when the release set breaks `docs/compatibility.md` (`Needs <x>` minimums
  of the collector / rum-api / grafana / plugin lines in use) and when `compose.images.yaml` /
  `.env.example` pins are not the newest releases. `--verify-digests` asks ghcr.io: with
  `GHCR_TOKEN` set it is a `curl -I` on `/v2/ouo11y/<image>/manifests/<tag>` with
  `Authorization: Bearer base64(token)` (GITHUB_TOKEN with `packages: read` works, and no
  `docker login` is left on the shared runners); otherwise `docker buildx imagetools inspect`.
- The old check compared against 0.3.0's compose, so the service blocks had silently drifted
  (rate-limit env, retention env, `-config.expand-env=true` for Loki / Tempo / Mimir, Loki's
  `runtime.yaml`, rum-api's admin / upload tokens and `internal` OTLP credential); fixed with
  the switch.

## What ships

`deploy/compose/quickstart.yaml`, generated by `deploy/scripts/gen-quickstart.sh`:

- The three ouo services use the released images (`ghcr.io/ouo11y/{collector,rum-api,grafana}`)
  at the pins in `compose.images.yaml`; Loki, Tempo and Mimir use the tags in the release's `compose.yaml`.
- Every file `compose.yaml` bind-mounts (collector `config.yaml` + `projects.htpasswd`, Loki,
  Tempo, Mimir, rum-api `config.yaml`, both Grafana provisioning files) is a top-level
  `configs:` entry with `content:`, mounted with `configs: - source/target`. That needs
  Compose >= 2.23.1; the header says 2.24 like `compose.images.yaml`.
- Same `OUO_*_PORT` / token variables and defaults as `compose.yaml`, so a `.env` next to the
  file works the same. No `name:`: the project is named after the folder. The first version had
  `name: ouo-quickstart`, and every copy on one machine was then the SAME project: a test copy's
  `docker compose down -v` removed the founder's own quickstart stack and its volumes (2026-10-23).
  Folder-named projects keep copies apart; the repo's `compose.yaml` keeps `name: ouo`.
- No demo backend (it is built from `examples/backend`, not a released image).

## Gotchas

- **Compose interpolates `configs.content`.** Every `$` in the inlined files is doubled by the
  generator (`sed 's/\$/$$/g'`), so the file reaches the container byte for byte:
  `${env:OUO_ALLOWED_ORIGINS:-...}` stays for the collector, `${OUO_READ_TOKEN}` for the
  Grafana provisioner, and `$${__value.raw}` in `datasources.yaml` arrives as `$${...}`
  (the provisioner's own escape). `docker compose config` prints the content re-escaped
  (`$$`), so check the file inside the container, not the `config` output.
- **rum-api runs as `nonroot` (65532).** A named volume mounted on a path that does not exist
  in the image (`/data`) is created `root:root` and rum-api cannot write replays. Mounting it
  on `/home/nonroot`, which exists and is owned by nonroot, seeds the volume with that owner
  (verified: `65532:65532 700`); `DATA_DIR=/home/nonroot` points rum-api at it. The
  contributor `compose.yaml` hides this because it bind-mounts `../data/rum-api`.
- The `grafana-plugin` init container from `compose.images.yaml` is kept: the `grafana-data`
  volume hides the plugin the image ships.

## Keeping it in sync

`gen-quickstart.sh --check` does two things and exits 1 on either:

1. diffs the committed file against a fresh render (catches a pin bump without a regenerate);
2. compares the hand-written service blocks with the release's `compose.yaml + compose.images.yaml`
   as `docker compose config --no-interpolate --format json` resolves both: same services,
   images, commands, entrypoints, ports and environment, and every read-only file the release
   bind-mounts (directories expanded file by file) must be a config at the same target. Allowed
   differences: no `backend` / `minio` / `minio-init`, rum-api's `DATA_DIR`, and the
   `grafana-plugin` init service (0.3.0's compose does not have it yet).

Tested (against the working-tree compose, before the switch to the release commit; same code
path): an env default changed in `compose.yaml`, and a new file under the provisioning
directory, both fail with a message naming the service and key; the first version of the
script failed it too (a trimmed `echo` line in `grafana-plugin`). CI job `quickstart` runs it
plus `docker compose -f quickstart.yaml config --quiet` when `deploy/compose/` or the script
changes; a release pin bump needs a regenerate (`docs/releasing.md`, step 9).
