# Source maps as write-once files keyed by debug id

Findings from the ADR-0022 prototype, 2026-11-13. They are what is not obvious from the ADR.

- **`ouo-sourcemaps upload` already sends what a pass-through route needs.** It PUTs a gzip body to `<url>/v1/sourcemaps?file=&debug_id=&release=` with the upload token. A route that only maps the token to a project and forwards the bytes is enough; the CLI uploaded to the prototype unchanged.
- **gzip bytes are not a stable identity.** Node's `gzipSync` gives the same bytes for the same input on one zlib version, so a repeat upload answers 200. Another Node or zlib version can compress the same map to other bytes, and a write-once store then answers 409. The debug id is already made from the map's content, so the CLI should treat 409 as "already stored" with a warning, not as a failure.
- **Every map can have an id.** rum-api keeps two indexes (debug id, release + path) and stores a map twice when it has both. Storing a map without a debug id under a UUID made from the SHA-256 of its bytes leaves one index. The release index becomes empty pointer objects, `release/<h(release)>/<h(path)>/<debug id>`, which are write-once too.
- **Pointers make "two builds of one path" visible.** With rum-api's release index the second upload replaces the first, and frames of the first build map to wrong lines (ADR-0011 section 6 worked around this with a debug-id check). With pointers there are two candidates and the resolver answers `ambiguous`. The rule "a frame with a debug id never uses the release" then needs no special case.
- **Write-once removes cache invalidation.** rum-api evicts a map on re-upload and other replicas wait for a TTL. A file that cannot change needs neither; only misses expire (60 s), which is also what lets a late upload apply.
- **An opaque store moves validation to the two ends.** rum-api parses a map on upload and rejects garbage with a 400. A store that does not parse accepts it; the resolver must treat an unreadable file as a miss and remember it like one. The CLI is where a wrong file should be caught.
- **dSYM upload needs one thing rum-api did on the server:** splitting a universal file into slices and reading each `LC_UUID`. With an opaque store the CLI does it (a fat header and one load command to read). Not built.
- **Hard link as the write-once check on a filesystem.** Write a temporary file, `link` it to the final name: the link fails when the name exists, and a reader never sees half a file. On S3 the same is a conditional put (`If-None-Match: *`).
- **The move is a move.** `stack.go` (frame parser) and the function-name, formatting and source-context helpers were copied from rum-api without a change; rum-api's web and Hermes fixtures pass against the new lookup.
