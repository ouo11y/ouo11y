OpenTelemetry data models

The one idea: everything nests the same way

Each signal is three layers. A request names who sent the data once, then which library, then lists the records. This is why batching is so cheap, and why choosing what goes on the outer layer matters so much.

Attribute values are an AnyValue: string, bool, int64, double, array, map or bytes, nested to any depth.

How the three signals connect: a log carries the ids as plain fields; a span has a parent and links; a metric has no ids at all, only optional exemplars.

Clocks. Every timestamp is the device clock in nanoseconds. OTel has no notion of skew. We tested Loki: a record 1 hour in the future is rejected with 400, and 400 means the client must not retry. A device whose clock is more than 10 minutes ahead silently loses its logs.

An Event is just a log record with a name. There is no separate event signal. The name promises a known shape for attributes and body.

Span events are going the same way. OTEP 4430 plans to deprecate the Span Event API and move instrumentation to log-based events, while the data shape stays in the proto. At spec v1.62.0 this is still a plan: AddEvent is not yet marked Deprecated, but the semantic conventions already recommend exceptions as logs.

Tested on Loki 3.7.9's native OTLP endpoint:

Loki 3.7.x has no mapping for the EventName field, so it isn't stored unless something copies it to an attribute first. Attributes are unaffected. Loki 4.0 (release candidates so far; source read, not run) stores it as event_name structured metadata.

A bytes body comes back as a base64 string, 4/3 the size. Bodies over 256 KB are rejected. Both matter for replay chunks.

Kinds: INTERNAL, SERVER, CLIENT, PRODUCER, CONSUMER. Status: leave Unset on success, Error on failure; Ok is only for a human assertion.

Sampling: the root span decides and the decision travels in the traceparent flags. If the browser starts the trace, its sampling rate decides what the backend records by default.

The client-side problem

This rules out a naive "one root span per session". Spans need to stay short and be tied together another way; Step 2 and 3 pick how.

Temporality

Every stream must have exactly one writer, and browsers are the awkward case:

  • Per-tab identity gives one new time series per page view for every metric. Mimir's default limit is 150,000 active series per tenant.
  • Shared identity gives thousands of writers on one series, which the spec calls an error state.
  • Delta alone does not fix this. Conversion expects aligned windows from one writer, and Mimir rejects delta by default.

The common way out is that clients send events and a server, as the single writer, aggregates them into metrics.

Cardinality: every distinct attribute combination is one series. Never put session.id, user ids or full URLs on a metric. The SDK's limit of 2000 protects one browser, not the total.

What each choice costs

One API call, 6 attributes, 7 resource attributes, random ids. Gzipped protobuf bytes per record, measured.

  • Batching decides size, much more than event versus span.
  • Event versus span differs by about 13 gzipped bytes. Choose on meaning, not size.
  • A metric is cheap because it throws the individual measurements away.
