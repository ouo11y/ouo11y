# Appendix D: OpenTelemetry-shaped web RUM

Status: research, 2026-10-29. This appendix covers the browser RUM SDKs whose data model is OpenTelemetry (or translates to it at the edge): Grafana Faro, the OpenTelemetry browser work (opentelemetry-browser, opentelemetry-js, opentelemetry-js-contrib, semantic conventions), Splunk, Honeycomb, Embrace, Elastic (classic agent and EDOT Browser), LaunchDarkly Observability (formerly Highlight.io), Dash0, plus short notes on Coralogix, HyperDX, Uptrace, OpenObserve. These are the projects closest to how `@ouo11y/browser` works (OTel JS SDK in the page, OTLP to a collector, rrweb beside it). Sections 2 to 7 of the shared structure are applied per project in D.1 to D.8; cross-project tables are in "Comparison".

Citation form: `alias/path:line`, where the alias and the tag / sha it was read at are defined once in the Sources table below. `[docs only]` = README, docs site or announcement, not verified in code. "measured here" = computed in this study from the published npm tarball (`npm pack --ignore-scripts`, then `gzip -9c | wc -c` on the shipped bundle). All repos were cloned blobless and checked out at their latest release tag on 2026-10-29; nothing was installed or built.

## 2–7. Per project

### D.1 Grafana Faro (deep)

**Packages.** `@grafana/faro-core` (API, metas, transports, batching), `@grafana/faro-web-sdk` (browser instrumentations and the fetch transport), `@grafana/faro-web-tracing` (OTel JS tracing), `@grafana/faro-react` (error boundary, profiler, React Router v4–v8 instrumentation, `faro/packages/react/src/router/`), and two experimental packages: `@grafana/faro-instrumentation-replay` and `@grafana/faro-transport-otlp-http` (`faro/experimental/`). Each package ships an IIFE bundle for a script tag next to the ESM build.

**The data model is Faro's, not OTel's.** The wire body is `{ meta, exceptions, logs, measurements, traces, events }` (`faro/packages/core/src/transports/types.ts:30-38`); `meta` holds `sdk, app, user, session, page, browser, view, k6, os, device` (`faro/packages/core/src/metas/types.ts:132-143`). Only `traces` is OTLP: the trace exporter serialises spans with `createExportTraceServiceRequest(spans, JSON_ENCODER)` and pushes the OTLP JSON object into the Faro payload (`faro/packages/web-tracing/src/faroTraceExporter.ts:13-19`). Everything else (logs, exceptions, measurements, events) is Faro JSON.

**Session.** Id = `genShortID()` = 10 characters from `crypto.getRandomValues` (`faro/packages/core/src/utils/shortId.ts:3-11`), overridable with `sessionTracking.generateSessionId` (`faro/packages/web-sdk/src/instrumentations/session/sessionManager/sessionManagerUtils.ts:23-27`). Limits 4 h max and 15 min inactivity, stored under `com.grafana.faro.session` (`…/sessionManager/sessionConstants.ts:3-13`). Default storage is `sessionStorage` (`persistent: false`, one session per tab, `…/VolatileSessionManager.ts:15-18`); `persistent: true` switches to `localStorage` and shares the session across tabs, adopting a session another tab rotated (`…/sessionManagerUtils.ts:103-111`). The previous id is kept as session attribute `previousSession` (`…/sessionManagerUtils.ts:177-180`). Lifecycle events `session_start`, `session_resume`, `session_extend` (`faro/packages/core/src/semantic.ts:4-6`). Sampling is per session through `samplingRate` or a `sampler` callback (`…/sessionManager/sampling.ts:5-12`). The collector can invalidate a session: a `202` with `X-Faro-Session-Status: invalid` makes the SDK extend into a new session (`faro/packages/web-sdk/src/transports/fetch/transport.ts:402-405`). Spans get `session.id` and `user.*` in `FaroMetaAttributesSpanProcessor.onStart` (`faro/packages/web-tracing/src/faroMetaAttributesSpanProcessor.ts:18-51`).

**Signals.** Default instrumentations: user actions, errors, web vitals, session, view, navigation, frustration, plus performance, CSP and console unless disabled (`faro/packages/web-sdk/src/config/getWebInstrumentations.ts:18-42`). Everything is a Faro event, measurement or exception; event names include `faro.performance.navigation`, `faro.performance.resource` (`…/instrumentations/performance/navigation.ts:45`, `resource.ts:54`), `faro.navigation`, `faro.user.action` (`faro/packages/core/src/api/userActions/const.ts:12`), `faro.frustration.<type>`, `securitypolicyviolation`, `route_change`, `view_changed`.

- **Web vitals**: `web-vitals/attribution` 6.x (`faro/packages/web-sdk/package.json` deps; `…/webVitals/webVitalsWithAttribution.ts:1`), sent as measurements. Attribution is flattened into values and context: INP carries `input_delay`, `processing_duration`, `presentation_delay`, the LoAF-based `total_script_duration`, `total_style_and_layout_duration`, `longest_script_*`, and, opt-in, the longest script's source URL / function (`…/webVitalsWithAttribution.ts:73-127`); LCP carries element, `resource_load_delay` etc. (`:130-165`); TTFB its DNS / connect / request / cache split (`:168-177`).
- **Soft navigations**: `NavigationInstrumentation` opens an activity window on `pointerdown` / `keydown`, merges HTTP, DOM-mutation and URL-change monitors, and emits `faro.navigation { fromUrl, toUrl, sameDocument, duration }` only when the window saw both a URL change and a DOM mutation, closing after 100 ms of inactivity (10 s drain cap) (`faro/packages/web-sdk/src/instrumentations/navigation/instrumentation.ts:13-50`). So a soft navigation has a measured duration, not just a URL.
- **User actions** (Faro's own interaction model, no zone.js): started by `pointerdown` / `keydown` (`…/userActions/instrumentation.ts:23-24`), named from `data-faro-user-action-name`, kept open while HTTP requests it started are pending (`…/userActions/userActionController.ts:54,94-95`, initial activity window 100 ms, max 1 s, `…/userActions/const.ts:1-5`). Client spans started during an action get `faro.action.user.name` / `faro.action.user.parentId` (`faro/packages/web-tracing/src/faroUserActionSpanProcessor.ts:24-37`). The tracer provider keeps OTel's default `StackContextManager` unless the app passes one (`faro/packages/web-tracing/src/instrumentation.ts:175`).
- **Frustration**: rage click = 3 clicks on the same target within 1 s and 100 px (`…/frustration/clickBurst.ts:2-5,33-35`); dead and error clicks use a 100 ms response window over HTTP, DOM-mutation and performance-entry monitors (`…/frustration/instrumentation.ts:13-14`); emitted as `faro.frustration.rage_click` etc. with target tag, coordinates and count (`:173-181`).
- **Network**: OTel `FetchInstrumentation` plus a Faro XHR subclass, `ignoreNetworkEvents: true` (`faro/packages/web-tracing/src/getDefaultOTELInstrumentations.ts:13-35`). Every CLIENT span is also re-emitted as a Faro event `faro.tracing.<scope>` with all span attributes, `duration_ns` and the span context (`faro/packages/web-tracing/src/faroTraceExporter.utils.ts:9-49`), so request analytics work from Loki alone without Tempo.
- **Errors**: client-side stack parsing (`faro/packages/web-sdk/src/instrumentations/errors/stackFrames/parseStacktrace.ts`, wired in `…/config/makeCoreConfig.ts:98`); consecutive identical exceptions are deduplicated (`faro/packages/core/src/api/exceptions/initialize.ts:122-130`); optional `fingerprint`.
- **Trace propagation** is wrapped in `FaroPausablePropagator`, which stops injecting `traceparent` when Faro is paused or (opt-in) the session is unsampled (`faro/packages/web-tracing/src/instrumentation.ts:168-176`); spans are not recorded while `document.prerendering` (`:139-147`). Resource attributes include `telemetry.distro.name = faro-web-sdk` and `browser.*` semconv keys (`:104-129`).

**Replay** (experimental since v2.1.0, 2025-11-28, commit 29d090c). `@grafana/faro-instrumentation-replay` records with a Grafana fork of rrweb (`@grafana/rrweb 2.0.0-grafana.2`, `faro/experimental/instrumentation-replay/package.json`). Defaults are strict: `maskAllInputs: true`, `maskTextSelector: '*'` (all text masked), fixed-length `******` input mask to avoid length leaks, `inlineStylesheet: false`, `recordAfter: 'load'`, 60 s inactivity pause (`faro/experimental/instrumentation-replay/src/const.ts:3-25`); built-in classes `grafana-mask`, `grafana-block`, `grafana-ignore`; canvas not supported (README). Transport: **every rrweb event becomes one Faro event** `faro.session_recording.event` with attributes `event` (the JSON-stringified rrweb event), `recording_id`, `gen`, `seq` (`…/src/instrumentation.ts:9,843-852`), plus `started` / `paused` / `resumed` lifecycle events (`:10-12,540,664`). It therefore rides the normal Faro batch (no per-chunk compression; gzip only when the transport's `requestCompression` is on, default off, `faro/packages/web-sdk/src/config/types.ts:6`). Recording ownership across documents uses a `localStorage` checkpoint and a `storage`-event takeover (`…/src/instrumentation.ts:132-153`). Grafana Cloud labels Session Replay public preview, opened to all stacks on 2026-10-14 `[docs only]`.

**Transport.** `FetchTransport`: batches of `itemLimit 50` / `sendTimeout 250 ms` (`faro/packages/core/src/config/const.ts:5-6`), flush on `visibilitychange: hidden` (`faro/packages/core/src/transports/batchExecutor.ts:30-32`) and `pagehide` (`faro/packages/web-sdk/src/transports/fetch/transport.ts:122`); buffer 30 requests, concurrency 5, 3 attempts with exponential backoff and jitter, retry on 408/425/429/5xx honouring `Retry-After`, keepalive under 60 000 bytes and 9 in-flight (`:20-31`, `deliveryQueue.ts:80-146,239`); optional gzip via `CompressionStream` (`transport.ts:67-71,417-423`); headers `x-api-key`, `x-faro-session-id`, a stable `Idempotency-Key` per batch (`:225-246`). No offline storage (no IndexedDB use anywhere in `faro/packages` or `faro/experimental`).

**Faro → OTLP.** The receiving side is the collector-contrib `faro` receiver (alpha for logs and traces, `occ/receiver/faroreceiver/metadata.yaml:10-11`), wrapped by Alloy as `otelcol.receiver.faro` and listening on `/` (`occ/receiver/faroreceiver/receiver.go:29,115`). Traces pass through as OTLP with `service.name` / `service.version` / environment from `meta.app` (`occ/pkg/translator/faro/faro_to_traces.go:20-40`). Logs, exceptions, measurements and events become OTLP log records whose **body is a logfmt line** of the item merged with all meta keys, with one attribute `kind` (and an exception hash) (`occ/pkg/translator/faro/faro_to_logs.go:125-158`, `logs_to_faro.go:31`). So in Loki a Faro web vital or replay event is a logfmt string, not structured OTel attributes. The experimental `@grafana/faro-transport-otlp-http` sends OTLP logs / traces straight from the browser (events become log records with `event.name`, `event.domain`, `event.attributes`; errors `faro.error.*`; measurements stay logs, `faro/experimental/transport-otlp-http/src/payload/transform/transform.ts:137-191`), but its README says the Grafana receiver does not accept that format and that Faro has no metrics (`faro/experimental/transport-otlp-http/README.md:1-15`). Grafana Cloud Frontend Observability requires `otelcol.receiver.faro` + `otelcol.exporter.faro` (Alloy docs) `[docs only]`.

**Vendor-neutral?** Yes with a collector in the middle: any OTel Collector contrib build (or Alloy) with the `faro` receiver turns Faro into OTLP logs and traces. The browser itself does not speak OTLP for anything but the embedded `traces` object.

**Footprint (measured here, shipped IIFE bundles, gzip -9).** `faro-web-sdk.iife.js` 126 190 B raw / 41 565 B; `faro-web-tracing.iife.js` 90 474 / 27 577; `faro-instrumentation-replay.iife.js` 212 618 / 63 933; `faro-core.iife.js` 26 219 / 9 019. A Faro page with tracing and replay is about 133 KB gzip in three script loads (bundles may duplicate shared code; Appendix M measures a real page).

### D.2 The OpenTelemetry browser work (deep)

**Where it lives (2026-10).** Three repos and the semantic conventions:

- **open-telemetry/opentelemetry-browser** (created 2025-09-11, first commit 030bdf3) is "the future home of the OpenTelemetry Browser SDK" and holds **event-based** instrumentations that emit log records (`ob/README.md:3-9`). Two packages, both experimental: `@opentelemetry/browser-sdk` 0.6.0 and `@opentelemetry/browser-instrumentation` 0.9.0 (`ob/README.md:91-96`). Maintainers come from Elastic, Embrace, Grafana Labs and Honeycomb, with an approver from Datadog (`ob/README.md:128-140`).
- **opentelemetry-js** 3.0 removed `@opentelemetry/sdk-trace-web` in favour of `@opentelemetry/sdk-trace` and points browser users to the browser-sdk repo (`ojs/packages/opentelemetry-sdk-trace-web/README.md:1-16`); `instrumentation-fetch` and `instrumentation-xml-http-request` are deprecated in favour of `@opentelemetry/browser-instrumentation/experimental/fetch` and `/xhr`, "the emitted telemetry differs significantly" (`ojs/experimental/packages/opentelemetry-instrumentation-fetch/README.md:6-10`). `@opentelemetry/web-common` keeps session helpers: `SessionSpanProcessor`, `SessionLogRecordProcessor`, `LocalStorageSessionStore` (key `opentelemetry-session`), `SessionManager` with `maxDuration` / `inactivityTimeout` (`ojs/experimental/packages/web-common/src/LocalStorageSessionStore.ts:9`, `SessionManager.ts:13-47`).
- **opentelemetry-js-contrib** keeps the span-based web instrumentations, now on core 3.0 / instrumentation 0.300: `instrumentation-document-load` 0.69, `-user-interaction` 0.68, `-long-task` 0.68, and the event-based `-browser-navigation` 0.17 and `-web-exception` 0.17 (`ojc/packages/*/package.json`). User interaction still needs zone.js for full async support (`ojc/packages/instrumentation-user-interaction/README.md:8-9`); the auto-instrumentations bundle README still sets up `ZoneContextManager` (`ojc/packages/auto-instrumentations-web/README.md:20-30`).

**browser-sdk 0.6.** `startBrowserSdk({ serviceName, exportConfig, logs, traces })` builds a logs SDK and a traces SDK with OTLP/HTTP JSON exporters, default endpoint `http://localhost:4318`, validating every URL before starting anything (`ob/packages/sdk/src/startBrowserSdk.ts:33-100`). Metrics are out of scope (`ob/packages/sdk/README.md:7-9`). Its default context manager is a plain synchronous stack (no async propagation, `ob/packages/sdk/src/core/context.ts`). It adds `browser.document.url.full` to spans and logs (`ob/packages/sdk/src/document/semconv.ts`) and `session.id` through session processors (`ob/packages/sdk/src/session/semconv.ts`). Session management: localStorage store, ids from a `Math.random` hex generator (`ob/packages/sdk/src/session/DefaultIdGenerator.ts:16`, same code in `ojs/experimental/packages/web-common/src/DefaultIdGenerator.ts:16`), **no built-in timeouts** (the 4 h / 30 min values in the docs are only the examples' choice, `ob/docs/session-management.md:118-131`), inactivity measured from `getSession()` calls rearmed at most every 5 s (`:86-93`), and no `session.start` / `session.end` events emitted.

**browser-instrumentation 0.9** (deps: `api-logs`, `instrumentation` 0.223, `web-vitals` ^6.2.3, `ob/packages/instrumentation/package.json`). Event names and attributes (`ob/packages/instrumentation/src/*/semconv.ts`):

| Instrumentation | Event (`event.name`) | Key attributes |
|---|---|---|
| navigation | `browser.navigation` | `url.full`, `browser.navigation.same_document`, `.hash_change`, `.type` (pushState / replaceState / popstate / Navigation API, `navigation/instrumentation.ts:27-29,103,143,223`) |
| navigation-timing | `browser.navigation_timing` | `browser.navigation_timing.*` and `browser.resource_timing.*` |
| resource-timing | `browser.resource_timing` | `browser.resource_timing.*` incl. `render_blocking_status`, `next_hop_protocol` |
| user-action | `browser.user_action.click` | `browser.mouse_event.button`, `browser.page.x/y`, `browser.tag_name`, `browser.css_selector`, `browser.element.attributes` |
| web-vitals | `browser.web_vital` | `browser.web_vital.name` (lower-case `lcp`…), `.value`, `.delta`, `.rating`, `.id`, `.navigation_type`; attribution only as raw JSON body when `includeRawAttribution` (`web-vitals/instrumentation.ts:124-147`) |
| console | `browser.console` | `browser.console.method` |
| errors | `exception` | `exception.type/message/stacktrace` (`errors/instrumentation.ts:21,123`) |
| fetch / xhr | spans | stable HTTP semconv plus `http.request.body.size` |

**Semantic conventions v1.44.0.** What is actually in the spec for the browser:

- `session.id`, `session.previous_id` (development) and events `session.start` (with `session.id`, optional `session.previous_id`) and `session.end` (`sc/model/session/registry.yaml:17-24`, `sc/model/session/events.yaml:2-40`). Session moved to schema v2 in PR #3983 (merged 2026-08-10, after v1.44.0).
- One browser event: `browser.web_vital` with attributes `browser.web_vital.name` (enum `cls, lcp, fcp, inp, ttfb, fid`), `.value`, `.delta`, `.id`, `.rating` (`good, needs_improvement, poor`), `.navigation_type` (`navigate, reload, back_forward, back_forward_cache, prerender`) (`sc/model/browser/events.yaml:2-19`, `sc/model/browser/registry.yaml:59-149`). The fields moved from the log body to attributes in PR #3851 (merged 2026-07-23), so older SDKs (Dash0, below) still put them in the body.
- Browser resource attributes `browser.brands`, `browser.platform`, `browser.mobile`, `browser.language`, and `browser.document.url.full` (PR #3633, `sc/model/browser/registry.yaml:8-53`).
- Mobile-oriented `app.*` that the web can reuse: `app.installation.id`, `app.screen.name/id`, `app.screen.click` and `app.widget.click` events, `app.crash.id` (`sc/model/app/registry.yaml:9-121`, `events.yaml:2-94`).
- **Not in semconv** (proposals closed or open): browser navigation (#2806 closed), navigation timing (#1919 closed), resource timing (#3069 closed), click / user action (#2992, #1941 closed), page view (#1910 closed), element timing (#4011 open), browser entity replaced by a public attribute group (#4172 open). So `browser.navigation`, `browser.resource_timing`, `browser.user_action.click`, `browser.console` are browser-SIG names emitted by code but not yet spec. There is nothing at all for replay, frustration signals, long animation frames or soft-navigation metrics.

**Vendor-neutral?** By construction. **Footprint**: tarballs 37 KB (`browser-sdk`) and 68 KB (`browser-instrumentation`) packed, ESM per entry, no prebuilt bundle; a real page cost depends on the OTel core packages it pulls (Appendix M).

### D.3 Splunk RUM, `splunk-otel-js-web` (deep)

**Packages.** `@splunk/otel-web` (RUM) and `@splunk/otel-web-session-recorder`; CDN builds are GitHub release assets (`splunk-otel-web.js` 512 413 B raw, `splunk-otel-web-session-recorder.js` 461 559 B raw, sizes from the v3.2.0 release API, not gzipped here). Built on `@opentelemetry/sdk-trace-web` 2.x and `web-vitals` 5.2.0 (`spl/packages/web/package.json:58-64`).

**Everything is a span.** Errors are spans named after the source with `component=error`, `error.message`, `error.stack` (4096 chars), plus `error.source_map_ids`: a JSON map of script URL → id read from `window.sourceMapIds`, which Splunk's build plugin injects (`spl/packages/web/src/instrumentations/splunk-error-instrumentation.ts:34-35,71-95,198-208`). Web vitals are zero-duration spans named `webvitals` with one numeric attribute per metric (`lcp`, `cls`, …), aligned with the document-load span when possible, and attribution attributes behind `_experimental_attribution` (`spl/packages/web/src/instrumentations/splunk-webvitals-instrumentation.ts:200-260`). Frustration signals are spans named `frustration` with `frustration_type` rage / dead / error / thrashed cursor (`…/frustration-signals/rage-click-detector.ts:150-151`, `dead-click-detector.ts:209-210`, `error-click-detector.ts:144`, `thrashed-cursor-detector.ts:538`). Also: long tasks, long animation frames (`…/splunk-long-animation-frame-instrumentation.ts:44`), WebSocket and socket.io, connectivity, page visibility, a "blocking element" tracker, and server-timing linking.

**Session.** 128-bit id (32 hex, `spl/packages/web/src/managers/session-manager/constants.ts:18`, generated at `session-manager.ts:240`), 4 h max, 15 min inactivity (`:19-21`), persisted in cookie `_splunk_rum_sid` (or `localStorage`), with a configurable cookie domain for cross-subdomain sessions (`spl/packages/web/src/managers/storage/constants.ts:21-25`, `storage-manager.ts:32-54`). An anonymous user id lives 400 days (`storage/constants.ts:24-25`). The attribute is **`splunk.rumSessionId`**, not `session.id` (`spl/packages/web/src/span-processors/span-attributes-processor.ts:103`); the exporter drops spans without it (`spl/packages/web/src/exporters/otlp.ts:51`). A `session.start` span marks a new session (`spl/packages/web/src/index.ts:668`).

**SPA navigation and async context.** Route changes are `routeChange` spans from patched `history.pushState/replaceState` and `hashchange` (`spl/packages/web/src/upstream/user-interaction/instrumentation.ts:91-92`, `…/splunk-user-interaction-instrumentation.ts:175`). A navigation-metrics manager waits for a quiet period and records `browser.navigation.page_completion_time`, resource counts and status `completed / interrupted / timeout` for both `documentLoad` and `routeChange` (`spl/packages/web/src/managers/navigation-metrics-manager/constants.ts`). Async context uses Splunk's own **731-line `SplunkContextManager`** that patches `setTimeout`, `Promise`, `MutationObserver`, event listeners (XHR, `hashchange`) and `MessageChannel` (`spl/packages/web/src/splunk-context-manager.ts:118-122,221-430`; wired at `index.ts:803`), i.e. a targeted zone.js substitute.

**Replay.** Since 2025-05 (PR #1075, `spl` commit 1e6ed5a) the recorder is no longer rrweb: `SessionReplay` is imported from `https://cdn.observability.splunkcloud.com/o11y-gdi-rum/session-replay/v2.18.1/session-replay.module.legacy.min.js` and bundled at build time (`spl/packages/session-recorder/src/session-replay/cdn-module.ts:20-33`); old rrweb options are migrated (`…/session-replay/config.ts:19-24`). Features: asset packing and caching, optional canvas, iframes and video, and a background-service iframe (`…/session-replay/recorder.ts:105-136`). Defaults: `maskAllInputs: true`, `maskAllText: true` (`:131-132`). **Transport is OTLP logs**: each segment (binary or JSON) is cut into ≤ 4000 KB pieces and each piece is one log record whose body is the bytes or string and whose attributes are `rr-web.chunk`, `rr-web.event`, `rr-web.offset`, `rr-web.total-chunks`, `segmentMetadata` (`:37,205-245`); resource attributes add `splunk.rumSessionId` and `user.anonymous_id` (`spl/packages/session-recorder/src/index.ts:163-172`). Default persistence of failed segments is IndexedDB (`persistence.ts:19-26`), which selects a hand-written OTLP **protobuf** log encoder (`otlp-proto-log-exporter.ts:64-72` and its `ProtoWriter`), gzip via `fflate.gzipSync` on the main thread, `keepalive` under 64 KiB (`:387-394`); the JSON variant is the same with `Content-Type: application/json` (`otlp-log-exporter.ts:41-45,235-242`). Endpoint `https://rum-ingest.<realm>.observability.splunkcloud.com/v1/rumreplay` (`index.ts:297`). The trace side marks sessions with replay through resource attribute `splunk.sessionReplay` (`spl/packages/session-recorder/src/index.ts:283`).

**Exporter.** OTLP/JSON traces by default when no `beaconEndpoint` is given; Zipkin remains for custom endpoints unless `exporter.otlp: true`, with a warning that Zipkin will be removed (`spl/packages/web/src/index.ts:525-533`). Realm URL `…/v1/rumotlp` (`:203-207`); the access token goes in the query string `?auth=` (`:211`). Sending is fire-and-forget: XHR normally, `navigator.sendBeacon` when `document.hidden` and the body ≤ 64 000 B (`spl/packages/web/src/exporters/otlp.ts:76-86`, `common.ts:30-50`); no gzip, no retry, no offline store for spans.

**Vendor-neutral?** Spans: yes, OTLP/JSON to any URL with `exporter.otlp: true` (the `?auth=` parameter is ignored by a stock collector). Replay: the format is OTLP logs, but the payload is Splunk's closed segment format and only Splunk's player reads it. Attribute names are Splunk's (`splunk.rumSessionId`, `location.href`, `component`, `app`, `browser.instance.id`), not semconv.

**Footprint (measured here).** The recorder's npm ESM is a prebuilt webpack bundle of 434 638 B raw / 124 330 B gzip -9 (includes the closed module and core-js); the RUM CDN file is 512 413 B raw (gzip in Appendix M).

### D.5 Embrace, `embrace-web-sdk` (deep)

**Stack.** OTel JS `sdk-trace` 2.12 (the new package, not `sdk-trace-web`), `sdk-logs` / `instrumentation` 0.223, OTel fetch and XHR instrumentations, `web-vitals` ^6.2.3, optional React (`emb/packages/web-sdk/package.json` deps). Pages are `app.surface.name` / `app.surface.id` (`emb/packages/web-sdk/src/constants/attributes.ts:31-33`).

**Signals.** Schema tag `emb.type` (`constants/attributes.ts:1,60-65`). Spans: document load and resource fetch, navigation (surface) spans, soft-navigation performance, element timing, user timing measures, network. Log records: web vitals, LoAF reports, rage clicks, first interaction, max scroll depth, DOM state, server timing, exceptions (`emb/packages/web-sdk/src/instrumentations/*`).

- **Web vitals** are OTel log records with the **semconv attribute names** `browser.web_vital.name/value/rating/id/delta/navigation_type` plus `emb.type = ux.web_vital` and flattened attribution under an `emb.` prefix: INP LoAF scripts, CLS layout shifts as JSON, TTFB sub-parts, LCP element (`…/web-vitals/WebVitalsInstrumentation/attributes.ts:1-13`, `WebVitalsInstrumentation.ts:85-260,530-569`); raw attribution optionally in the body.

- **Rage click**: 3 clicks within 500 ms (`…/rage-click/RageClickInstrumentation/constants.ts:2-5`).

**Export.** To Embrace: gzip-mandatory OTLP/JSON to `<data-url>/v2/spans` and `/v2/logs` (`emb/packages/web-sdk/src/exporters/EmbraceTraceExporter/utils.ts:4`, `EmbraceLogExporter/utils.ts:4`), keepalive, concurrency 5, 30 s timeout (`exporters/constants.ts:1-7`); the fetch transport tracks Chrome's 64 KiB / 9-request keepalive budget and gzips with `CompressionStream` (`transport/FetchTransport/FetchTransport.ts:8-30,74-79,150-201`) and a retrying transport wraps it (`transport/RetryingTransport/`). **To anyone else**: `appID` is optional when `spanExporters` or `logExporters` are given (`emb/packages/web-sdk/src/sdk/types.ts:271-311`, check at `initSDK.ts:151-158`); the README shows stock `OTLPTraceExporter` / `OTLPLogExporter` (`emb/packages/web-sdk/README.md:277-290`). No offline store, no replay on the web.

**Footprint (measured here).** CDN `embrace-web-sdk.js` (IIFE, minified, OTel included): 226 781 B raw / 60 532 B gzip.

### D.8 Dash0 and the rest (deep on Dash0)

**Dash0 `@dash0/sdk-web` 0.28.3 has no OpenTelemetry JS dependency at all.** Its only runtime dependency is `web-vitals` ^5 (`d0/package.json` deps; `@rrweb/record` is bundled into a separate recording entry). It writes OTLP/JSON by hand (`d0/src/types/otlp.ts`, `d0/src/utils/otel/`), wraps fetch and XHR itself (`d0/src/instrumentations/http/`), and wraps event handlers and timers to catch errors with useful stacks (`d0/src/instrumentations/errors/event-handlers.ts`, `timers.ts`). It is the closest existing design to "OTLP from the browser without the OTel SDK weight".

- **Session**: `localStorage` key `d0_session` = `id#start#lastActivity`, inactivity 3 h, termination 6 h, both capped at 24 h (`d0/src/api/session.ts:12-36,103`). Id = 8 bytes, the first byte a flag byte (ephemeral when localStorage is unavailable) (`d0/src/utils/session-id.ts:1-26`, `utils/id.ts:1-6`). Attributes `session.id`, `page.load.id`, `browser.tab.id`, `browser.window.width/height` (`d0/src/semantic-conventions.ts:23-28`). Deterministic per-session sampling (`d0/src/types/options.ts:110`).
- **The session id is embedded in every trace id**: `d042` + flag byte + 8-byte session id + random (`d0/src/utils/trace-id.ts:1-25`). Any backend span in the propagated trace therefore carries the browser session in its trace id, with no baggage needed.
- **Events** (log records with `event.name`): `browser.page_view` (with `pushState` / `replaceState` change state for SPA navigations), `browser.navigation_timing`, `browser.web_vital`, `browser.error`, `browser.session_recording`, `browser.rage_click` (`d0/src/semantic-conventions.ts:73-106`). Web vitals: LCP, INP, CLS only, `reportAllChanges: true`, with name / value / delta **in the body** as a kvlist (`d0/src/instrumentations/web-vitals.ts:1-34`), i.e. the pre-PR-3851 semconv shape.
- **Replay as OTLP logs**: rrweb events are chunked; each chunk is one log record, `event.name = browser.session_recording`, body = the chunk JSON string, attributes `dash0.session_recording.id/seq/event_count/has_snapshot/end_time_unix_nano`, and the trace / span id of the recording stream (`d0/src/instrumentations/session-recording/log.ts:17-47`). Chunks bypass the log batcher and go out alone to `/v1/logs`, gzip by default ("replay JSON compresses roughly 8:1"), uncompressed during unload because `CompressionStream` is async (`d0/src/transport/index.ts:50-80`). Rage clicks are only detected while recording (`d0/src/instrumentations/frustration/rage-click.ts:40`).
- **Transport**: `fetch` with `Authorization: Bearer`, optional `Dash0-Dataset`, keepalive under 60 000 B and ≤ 15 pending, gzip off by default for ordinary batches (`d0/src/transport/fetch.ts:8,30-70`, `d0/src/vars.ts:249`). Multiple endpoints supported. No retry store.
- **Vendor-neutral?** Yes: standard OTLP/JSON `/v1/traces` and `/v1/logs` with standard auth headers; replay is ordinary OTLP logs a collector can route (only Dash0's UI plays it).
- **Footprint (measured here)**: `dash0.iife.js` 89 429 B raw / 27 484 B gzip; `dash0-session-recording.iife.js` 76 024 / 22 650.

## 9. Questions asked and answers

1. **Does any OTel-shaped vendor send replay over OTLP?** Yes, three ways: Splunk (one log record per ≤ 4 MB segment piece, protobuf + gzip, closed recorder, `spl/…/session-replay/recorder.ts:205-245`), Dash0 (one log record per rrweb chunk, gzip per request, `d0/src/instrumentations/session-recording/log.ts:29-47`), Faro (one Faro event per rrweb event, becomes one logfmt log line per event in the collector, `faro/experimental/instrumentation-replay/src/instrumentation.ts:847-852`). HyperDX inherits the old Splunk rrweb-over-OTLP-logs shape. LaunchDarkly uses GraphQL. ouo uses its own receiver.
2. **Is there a semconv for replay?** No. Nothing for recording id, chunk sequence or snapshot markers in v1.44 (`sc/model/` has no replay group); the three vendors use `rr-web.*`, `dash0.session_recording.*`, Faro `recording_id/gen/seq`.
3. **Who stamps `session.id` and who refuses?** Faro, OTel, Honeycomb, Dash0, ouo stamp it; Embrace refuses on purpose (`emb/…/EmbraceUserSessionManager/README.md:403-407`); Splunk and LaunchDarkly use vendor keys.
4. **Does anyone use zone.js by default?** No. Splunk and EDOT ship their own targeted patching context managers; Faro, Embrace, LaunchDarkly, the OTel browser-sdk use a stack manager; Honeycomb leaves zone.js optional; contrib user-interaction still recommends it.
5. **Who uses Long Animation Frames for INP?** Faro (summary fields, `webVitalsWithAttribution.ts:98-121`), Honeycomb (child spans per frame and script, `web-vitals-autoinstrumentation.ts:425-480`), Embrace (`loaf_scripts` attribute), Splunk (separate LoAF instrumentation). ouo reports INP without attribution.
6. **Does any of them keep data offline across page loads?** Only Splunk's replay segments (IndexedDB inside the closed module, `spl/packages/session-recorder/src/persistence.ts:19-26`). No RUM span/log pipeline in this group persists failed batches; ouo does (IndexedDB store, `sdk/browser/src/transport/store.ts`).
7. **Session id entropy?** Splunk 128 bit, ouo UUID v4 (122 bit, `crypto.randomUUID`), Faro 10 chars from `getRandomValues`, Dash0 56 bit + flag, OTel `browser-sdk` / `web-common` 128-bit hex from **`Math.random`** (`ob/packages/sdk/src/session/DefaultIdGenerator.ts:16`).
8. **Does the OTel browser-sdk emit `session.start` / `session.end`?** No; the semconv events exist (`sc/model/session/events.yaml`) but `SessionManager` only notifies observers (`ob/packages/sdk/src/session/SessionManager.ts`, `ob/docs/session-management.md:93-94`).

## 10. Takeaways for ouo

**What ouo already does (same as the field).** OTel JS traces + logs in the page; OTLP/JSON to a collector; `session.id` on every span and log; W3C `traceparent` to the backend; rrweb replay beside OTel; semconv `exception.*`; keepalive budget handling; gzip with `CompressionStream`. The browser-SIG direction (events as log records with `event.name`, sessions as attributes) is the model ouo chose in Phase 2.

**What ouo does better than this group.**
- **Delivery**: retry plus an IndexedDB offline store (5 MB / 24 h) for spans, logs and replay; nobody else in the group persists RUM batches, and Splunk's span exporter is fire-and-forget.
- **Page-hide correctness**: ouo's own batcher flushes concurrently at hide and re-emits INP from its own `visibilitychange` / `pagehide` listeners (kb `otel-browser-sdk.md` items 22–23); Faro and Dash0 flush on hide but go through a single queue, the OTel batch processors serialise flushes.
- **Semconv session events**: ouo is the only SDK here that emits `session.start` / `session.end` log records as specified.
- **Backend session correlation through baggage** (`session.id`, `user.id` merged at inject time), which works for any backend; Dash0's trace-id embedding is clever but proprietary and only Dash0 decodes it.
- **Multi-tab replay lease** (BroadcastChannel, one recording tab, `ouo.tab` markers) is more careful than Faro's per-document checkpoint and close to Embrace's "one engaged tab" rule.
- **Structured data end to end**: ouo's events stay attributes in Loki; Faro's production path flattens every item into a logfmt body (`occ/pkg/translator/faro/faro_to_logs.go:146-154`).

**What ouo should copy (ranked).**
1. **Rename to semconv web vitals now**: event `browser.web_vital`, attributes `browser.web_vital.{name,value,delta,id,rating,navigation_type}`, lower-case names (`sc/model/browser/registry.yaml:59-149`; OTel and Embrace already do). Keep the `ouo.*` keys one release for rum-api and the plugin, then drop them.
2. **Web vitals attribution with LoAF**: INP input delay / processing / presentation split, longest script and its source, LCP element and sub-parts, CLS largest shift target (Faro's flattened fields are the lightest model, Honeycomb's child spans the richest).
3. **Frustration signals**: Faro's rage / dead / error click design (3 clicks, 1 s, 100 px; 100 ms response window over HTTP, DOM mutation and performance entries) is small and fits ouo's existing InteractionTracker; Splunk adds thrashed cursor.
4. **Soft-navigation duration**: Faro's activity window (URL change + DOM mutation, closes after 100 ms idle) gives each SPA navigation a duration; Embrace shows how to prefer Chrome's `soft-navigation` entries when present.
5. **Replay as OTLP logs, as an option**: Dash0 proves a chunk-per-log-record design works through a stock collector (`event.name = browser.session_recording`, chunk JSON as body, recording id / seq / has_snapshot attributes, gzip per request, no gzip at unload). Offering it behind a flag would let ouo replay ride any OTLP pipeline without the 4319 receiver, while keeping the receiver for rum-api.
6. **`telemetry.distro.name` / `.version`** on the resource (Faro does it, `faro/packages/web-tracing/src/instrumentation.ts:129`).
7. **Collector-side session invalidation** (Faro's `X-Faro-Session-Status: invalid`) and Splunk-style `error.source_map_ids` (debug-id map) are worth keeping on the list for the source-map work.
8. **Prepare for OTel JS 3.0**: move from `sdk-trace-web` to `sdk-trace` (Embrace already did) and plan the fetch / XHR switch to `@opentelemetry/browser-instrumentation`, whose spans differ.

**Where ouo could contribute upstream.**
- **semantic-conventions**: a replay / session-recording proposal (recording id, sequence, full-snapshot flag, chunk time range as log attributes on a `browser.session_recording` event) using ouo, Dash0, Splunk and Faro as prior art; frustration signals (`browser.rage_click`, dead click); support for the open element-timing PR #4011 and for re-opening navigation / soft-navigation events (#2806 closed).
- **opentelemetry-browser**: `crypto.getRandomValues` for the session id generator (`ob/packages/sdk/src/session/DefaultIdGenerator.ts:16` and `ojs/experimental/packages/web-common/src/DefaultIdGenerator.ts:16` use `Math.random`); `session.start` / `session.end` emission from `SessionManager`; a batch processor that flushes at `pagehide` without serialising (ouo's item 22 finding); INP-at-hide handling; cross-tab session sync via the `storage` event.

**Not to copy.** Splunk's closed recorder and query-string token; Faro's one-event-per-rrweb-event replay transport (per-event overhead, logfmt in Loki); Honeycomb's per-page-load sessions; Embrace's refusal of `session.id` (ouo's plugin, rum-api and the semconv all key on it).
